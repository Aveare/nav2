> 适用条件:**云台未装机、发射机构未修复**,只有底盘可测。
> 与 `.Doc/底盘首测步骤卡.md` 的关系:本文件是它的**升级版**,取代其执行部分;
> 首测步骤卡保留作历史记录。计划层面的排期见 `.Doc/底盘优化计划.md` 与 `.Doc/装机后总计划书.md`。

## 0. 当前能测什么、不能测什么

先看代码事实(2026-11-15 核对),这决定了测试边界:

| 遥控右开关 | 模式 | 云台未装时是否可用 |
|---|---|---|
| **上挡** | `CHASSIS_ZERO_FORCE`(kill authority,四轮 `DJIMotorStop`) | ✅ 可用。推车测逆解靠它 |
| **中挡** | `CHASSIS_FOLLOW_GIMBAL_YAW` | ❌ **不可用**。`wz` 由 `offset_angle` 驱动,而 `offset_angle` 来自 **yaw 电机单圈 ecd**;云台没装 → 该值恒为 0 → `offset = −YAW_ALIGN_ANGLE` 恒为非零常数 → **底盘持续自转** |
| **下挡** | `CHASSIS_ROTATE`(`wz = CHASSIS_ROTATE_SPEED`,写死宏) | ✅ 可用。自转 + 平移叠加可测 |

**核心限制:平移(vx/vy)没有独立入口。**
`CHASSIS_NO_FOLLOW` 这个模式在 `chassis.c:255` 有实现(`wz≡0`),但 `robot_cmd.c` 的遥控/键鼠**都没绑**,只有裁判系统 UI 交互(`referee_task.c:161`)能间接切——而裁判系统当前未接(`[referee] waiting for robot_id`)。

→ **结论:不改代码的话,平移没法通过遥控测。**

### 0.1 可选解锁项(需烧一次固件)

在中挡分支加"云台离线则降级为 NO_FOLLOW",改动约 6 行,好处是**平移测试不再被云台阻塞**:

```c
/* robot_cmd.c: RemoteControlSet() 中挡分支内 */
else if (switch_is_mid(rc_data[TEMP].rc.switch_right))
{
    /* 云台未装/未上电时 yaw ecd 恒 0,FOLLOW 会把底盘带成持续自转;
     * 降级为 NO_FOLLOW:wz=0,保留全向平移,用于底盘单独测试 */
    if (!GimbalOnline())
        chassis_cmd_send.chassis_mode = CHASSIS_NO_FOLLOW;
    else
        chassis_cmd_send.chassis_mode = CHASSIS_FOLLOW_GIMBAL_YAW;
    gimbal_cmd_send.gimbal_mode = GIMBAL_GYRO_MODE;
}
```

`GimbalOnline()` 需新写(判 `yaw_motor->daemon` 在线 + `feedback_received`),约 5 行。
**回退**:删掉该 if 即恢复原行为。**风险**:低——只影响云台离线这一种情形。

> 不烧这一版也能测 A/B/C1/C2/E 各项;**只有 C3、D、B3 的"驱动力矩下平移"需要它**。

## 1. 准备

### 1.1 硬件与场地

- 车四轮着地,电池满电(**测试全程看电压,低于 22V 的数据作废**——电压降会改变所有速度/功率结论)
- 场地:平整硬地,自转半径留 ≥1m 净空;直线测试需 ≥3m 直线通道
- 工具:卷尺(2m 以上)、胶带(贴起终点线)、手机秒表、记号笔
- **车身上贴一个指向标记**(胶带剪个箭头),所有自转/朝向测试靠它对齐

### 1.2 采样工具(已就绪)

| 工具 | 用途 | 采样率 | 备注 |
|---|---|---|---|
| `node tools/sample_scalars.js --seconds N --vars est_vx,est_vy,est_wz --out build/xx.csv` | 连续采样标量 | **约 3Hz**(每点建一次临时连接,约 330ms) | 逐点落盘,可边采边看 |

**必须知道的三个工具事实**(否则会读错):

1. `variables.read` **不支持复合类型**。`motor_lf->measure.speed_aps` 会**静默返回垃圾**(它把 `->` 当成指针变量自身+偏移)。只能读顶层标量:`est_vx/est_vy/est_wz`、`vt_lf..rb`、`chassis_last_ms`、`motor_lf`(指针本身)。
2. `memory.read` **必须在暂停的调试会话里**。运行态调用返回 `Pause the debugger before inspection`。
3. `motor->feed_cnt` **不是帧计数**,是 `DWT_GetDeltaT()` 的时间戳(µs),约 71.6min 回绕。**在线判据用 `dt`(距上一帧时间)< 5ms**。

## 3. B 组:零力推车——逆解验证(核心,30 分钟)

**目的**:验证 `EstimateSpeed()` 逆解链(轮径 75 / 减速比 19 / 0.7071 几何因子)是否正确。
**方法**:上挡(零力),人推车,用 `est_*` 积分与地面真值比。

### B1 直线 2m(**最重要**)

1. 地面量 **2000mm**,起点/终点各贴一条胶带
2. 车头前沿对准起点线,车身摆正
3. **慢推**(约 0.2m/s,2m 用 10 秒),全程四轮着地、不拐弯
4. **判决量:轮端里程计**(推车前 mark、推车后 delta;中间不采样,没有空窗)
   ```bash
   node tools/odom.js mark B1-slow            # 推车前:车静止、四轮着地
   # —— 慢推 2m,车头停在终点线 ——
   node tools/odom.js delta B1-slow --expect 2000
   ```
   `distanceMm` = 四轮位移中位数;`wheelSpreadPct` = 四轮离散度(>5% 说明有轮在拖/滑)。
5. **可选:同步跑 PC 采样**,只取速度波形与符号,**不用来算位移**
   ```bash
   node tools/sample_scalars.js --seconds 30 --vars est_vx,est_vy,est_wz --out build/B1.csv
   ```
   `∫est_vx dt` 仅在无丢点时可信:7Hz 以下采样率下,丢点 1 个就足以让积分失真几十毫米。

**判据**

| 结果 | 结论 |
|---|---|
| 2000 ± 60mm(±3%) | ✅ 逆解链正确,轮径 75 可信 |
| **四轮离散 > 5%** | 某轮拖轮/打滑/未着地,先修机械,比例问题暂不判 |
| ≈ 1434mm 且四轮一致 | 比例错(与速度无关)→ 查 B2 |
| 偏差 >10% 且方向不一致 | 查 `RADIUS_WHEEL` / `REDUCTION_RATIO_WHEEL` |

> **背景订正(2026-11-15)**:原本记的「快推实测 1434mm = −28%」**是积分假象,不能作为结论**。
> 复盘 `build/sample_straight.csv`:推车段为 19609→23553ms(峰值 653mm/s),只积到最后非零点得 **1444mm**;
> 而第 68→69 行间隔 **3475ms**(探针丢点),跨越该空洞按梯形补齐会多算 **842mm**,得 2287mm。
> 真空值落在 1444~2287 之间,空洞期间车仍在滑行,**无从判定**。该次数据只能证明「推得很直」
> (航向 +0.2°、横向 +19mm),不能证明比例错。重测一律用 `tools/odom.js`,PC 采样只当波形参考。

### B2 快推 vs 慢推对比 —— **已取消(判别门限低于方法噪声)**

原设计:打滑与速度相关、比例错与速度无关,用两次速度的读数差来分。
**2026-11-15 实测推翻了它的前提**:同一条线两次"推 2 米"读出 2000.2 与 2065.2,**差 3.25%** ——
手推的起终点对齐与推车路线误差本身就是 ±3% 量级,而 B2 要判的"打滑 vs 比例错"差异门限也在 3% 量级。
**方法分辨率不够,做两次也分不出来。**

改为:**只在快推读数偏离慢推 >10% 时**才当作打滑线索追查;正常情况下不做本项。
比例正确性已由 B1 的 +0.01% 直接定案(比例若错 1/√2 会偏 29%,一眼就能看出)。

### B3 反向直线(符号检查)——**手推无意义,已降级**

`EstimateSpeed()` 是四轮转速的**齐次线性组合**(chassis.c:231),四轮同时取反则 `est_vx` 必然取反,不存在"反向符号错"的可能。
所以手推反向推车**在数学上是多余的**,2026-11-15 实测也证实:所谓反向推车读出的符号模式与 B1 前进一位不差,车其实是车头朝前动的。
真正需要物理验证的是**指令→实际速度**(逆解四轮转速对不对、速度环跟不跟得上),那必须驱动才能测。

> 本项改为:**只在能发速度指令时做**(需要能进 NO_FOLLOW 或有人扶着车驱动),用手推不必做。
> 注意 `delta --expect -2000` 的负号只影响 `errorPct`,不影响 `distanceMm` 的符号——符号由轮子实际转向决定。

### B4 横移(手推即可,不需要 0.1 解锁项)

车头指向不变,人从车体中心把车推到侧面 **2m**(匀速约 0.2m/s,四轮着地不带转),用轮端里程计判读:

```powershell
node tools/odom.js mark B4-vy
# 推完
node tools/odom.js delta B4-vy --axis vy --expect 2000
```

判据:`distanceMm` ≈ ±2000(±3%),符号告诉你**本车 +vy 指向哪一侧**(2026-11-15 实测 +2054.2 = +2.71%,+vy = 车头左侧)。
四轮离散 >15% 说明横移打滑严重,数据只能定性用。

> 手动推车不需要 NO_FOLLOW 入口,旧版"本条跳过/标阻塞"作废。

### B5 原地转(仅验符号,不验力臂)

人扶着车体**原地翻转一整圈**(俯视逆时针,绕车体中心转,不要平移),用 `--axis wz` 判读偏航角:

```powershell
node tools/odom.js mark B5-turn
# 转完
node tools/odom.js delta B5-turn --axis wz --expect 360
```

判据(2026-11-15 实测 +347.3° 定案):
- **符号**:俯视逆时针转 → `yawDeg` 为**正**。即 **本车 +wz = 俯视逆时针(RM 标准)**,跟随律/自瞄/导航都用这个约定;
- **量级**:一圈应 ≈ ±360°,手推对不准圈数 + 麦轮横滑,±10% 内都算正常,**不要拿它标定力臂**;
- **四轮离散 <1% 才算正常**(实测 0.2%),大了说明某个轮子没着地或在拖。

> **重要:这项不用于验收力臂**。2026-11-15 实测麦轮原地自转辊子横滑 10~20%,
> 方法误差大于要判的门限(<10%),**方法本身不成立**。
> **力臂 340mm 直接取几何值** `√(250² + 230²) = 339.7mm`,由已实测的 `WHEEL_BASE 500` / `TRACK_WIDTH 460` 决定。

## 4. C 组:自主驱动(下挡小陀螺,30 分钟)

### C1 架空转向检查(先做,避免落地跑飞)

四轮垫离地 2~3cm,下挡启动,**低速**观察(下挡固定 300°/s,只看 1~2 秒即停):

| 现象 | 结论 |
|---|---|
| 四轮都朝同一方向转,车体(想象)顺时针/逆时针一致 | ✅ 正常 |
| 某一个轮反向 | 该轮 `motor_reverse_flag` 或 CAN ID 配错 |
| 对角两个反向 | 两对安装方向相反 |
| 四个全反 | 整体符号取反(不影响性能,只影响指令方向定义) |

### C2 小陀螺转速验证(**12 秒定案正解链**)

1. 落地,车头标记对准参照物
2. 下挡启动,同秒开始秒表
3. **数 10 圈**(300°/s × 12s = 3600°)
4. 停表,记录

| 实测 10 圈耗时 | 结论 |
|---|---|
| **12.0 ± 1.0 s** | ✅ 正解链正确,`wz=300` 名副其实 |
| ≈ **17 s**(实际 212°/s) | 偏差 1/√2 → `0.7071` 因子有问题 |
| ≈ 8.5 s | 偏快 1.4 倍,同上反向 |

> 这是**唯一不需要采样工具、只需要秒表**的关键测试,且直接验正解链(指挥的速度是否 = 实际速度)。
> 2026-11-09 "指令 300 实测 375" 曾做过同类测量,结论支持 `0.7071` 正确;本次因轮径/轴距都改过,需重测。

### C3 小陀螺 + 平移(需 0.1 解锁项)

下挡,同时推右杆平移。观察:

- 车是否沿"当前朝向"平移(小陀螺时车头在转,平移方向应随车头转)
- 有无明显打滑(车辆实际轨迹与预期方向的偏差)
- 记录 `CHASSIS_TRANSLATE_BIAS_ANGLE`(当前 +10°)是否仍然合适

### C4 三档转速(可选,需重烧 3 次)

`chassis.c` 里 `wz = CHASSIS_ROTATE_SPEED` 是写死宏。要测 100/200/300 三档,需改宏重烧 3 次。

> **450 档不要试**:按当前几何,450 档理论需 6449 RPM,会被 `CHASSIS_MAX_MOTOR_RPM=6000` 削到
> **约 419°/s**。那是物理上限,不是故障。

## 5. D 组:功率数据采集(为 P2 功率控制备料,20 分钟)

**背景**:2027 协议 0x0202 的电压/电流/功率**全是保留位**(已核对官方手册),裁判只给 `buffer_energy`(10Hz)。
所以功率控制只能自建模型 `P ≈ Σ(τ·ω)`,`ω` 来自轮速、`τ` 来自电流 —— **B 组的数据质量直接决定功率估算精度**。

**前置**:把 `CHASSIS_CALIB_LOG` 改回 1 重烧(现在因 RTT 溢出被置 0),或用 RTT 读 `[chcal]`。

| 编号 | 工况 | 记录 |
|---|---|---|
| D1 | 匀速直行 3 档(约 300/600/900 mm/s),各 10s | 各轮电流、`buffer_energy` 斜率、电压 |
| D2 | 急加速 / 急停(满杆起停)各 5 次 | 电流峰值、`buffer_energy` 最低点 |
| D3 | 连续小陀螺 60s | 稳态电流、温升、`buffer_energy` |

**判据**:全程 `buffer_energy` 不低于 **40J**(低于此值继续大功率机动有断电风险)。
若 D3 跑完 `buffer_energy` 仍在 60J 以上,说明当前整车功率远低于限值,**功率控制可延后到发射/自瞄全开后再做**。

## 9. 排查表

| 现象 | 最可能原因 | 下一步 |
|---|---|---|
| 四轮全不动,`online=false` | 电调未上电 / CAN 未接 | 量 24V、查 CAN 线 |
| 中挡车持续缓转 | **正常**(云台未装,`offset` 恒非零) | 用上挡/下挡,或做 0.1 解锁项 |

### 11.3 重标 `YAW_CHASSIS_ALIGN_ECD`(云台装好后,消除中挡自转)

**一个宏修两件事**:`CalcOffsetAngle()`(`application/cmd/robot_cmd.c:283-292`)算

```
offset = yaw_motor_single_round_angle − YAW_ALIGN_ANGLE
YAW_ALIGN_ANGLE = YAW_CHASSIS_ALIGN_ECD × ECD_ANGLE_COEF_DJI    // robot_cmd.c:27,系数 = 360/8192 = 0.043945
```

这个 `offset` 同时喂给 ① 解锁回正(`robot_cmd.c:492-514`)和 ② 中挡底盘跟随
(`chassis.c:258-288`,FOLLOW)。**宏值失真 → 回正以 90°/s 追一个追不上的角(3s 上限 270°),表现为
yaw 持续自转,底盘也跟着自转。** 云台拆装后 yaw 电机与车体的相对零位变了,所以必须重标。

**当前值**:`YAW_CHASSIS_ALIGN_ECD 3564`(`config/robot_infantry_2026.h:22`)= 156.62°。
云台未装时布局使 yaw 单圈角≈0 → offset ≈ **−156.6°**,这就是 2026-11-15 观察到的自转来源。

**操作(约 1 分钟,需要人配合)**:

1. 云台装好、上电;**遥控右上挡**(kill switch,全零力,电机不抗力,手能自由转云台);
2. 手动把云台转到**与车头正前方对齐**的位置并保持不动 —— 对齐基准是**车体纵轴**(看车架/轮子),
   不是云台自己的外壳缝;
3. 跑 `node tools/read_yaw.js`(要 `--json` 就加参数);
4. 把输出里的 **`建议宏:YAW_CHASSIS_ALIGN_ECD=<n>`** 写进 `config/robot_infantry_2026.h:22`;
5. 编译烧录(这属于参数级改动,不需要结构级批准;烧录由用户执行);
6. 拨**中挡**验证:云台应在 **≤3s** 内回正到车头方向并停住,底盘**不自转**。

**读工具输出怎么判**:

| 字段 | 含义 | 判据 |
|---|---|---|
| `yaw 电机:在线` | dt<5ms,正在持续收 CAN 帧 | 掉线时 ecd 是冻结值,标定必错,工具直接 `ok:false` |
| `ecd=` / `单圈角=` | 当前编码器计数与角度 | 两者应自洽(`ecd×0.043945`),工具会打印交叉校验行 |
| `当前宏 … 此刻 offset=` | 用现有宏算出的 offset | 这就是"自转的元凶"有多大 |
| `建议宏 … 校准后 offset=` | 写进去之后 offset 会变成多少 | 应当 ≈0.00° |

**两个不要搞错的点**:

- **方向反了(越转越远)不要改 ecd**,改 `GIMBAL_RECENTER_DIR`(`config/robot_infantry_2026.h`)的符号;
  ecd 只管"哪儿是零",方向管"往哪边转"。
- 读数时云台**必须在动过之后停稳再读**,否则 ecd 每次不同;工具里"ecd 与角度反算差 >1 计数"就是
  在提示这一点。

**前提**:`variables.read`/`memory.read` 需要能连上目标 → 探针插好、`debug.js --start --attach` 已建会话
(`tools/read_yaw.js` 会检查,缺了会直接告诉你要跑哪条命令)。MCP 通道 2026-11-15 已修好,也可以直接用
`mcp__emberprobe__*` 读同一批数据。

### S0 前置:CAN1 电机总闸(按需,不用遥控上挡)

台架上想"电机一律不出力"时,不必靠遥控上挡(kill switch)。有**软**和**硬**两种:

**硬锁(编译期,防疯车):** `modules/motor/DJImotor/dji_motor.h` 的 `DJI_MOTOR_CAN1_FORCE_DISABLE`
- `=1` → CAN1 四轮 + yaw **永久零输出**,运行期改 `g_dji_can1_enable`、调 `DJIMotorSetCAN1Enable(1)`
  都会被拒,连调试器也绕不过;构建日志会打 `#pragma message` 提醒。
- `=0` → 正常。**跑 S1/S2/E1 等需要电机出力的测试前必须改回 0 重烧。**
- 当前仓库内值:**1(安全版)**。

**软总闸(运行期,不用重烧):**

```powershell
# MCP:把总闸关掉(0 = CAN1 上四轮 + yaw 全部零输出,反馈照常)
mcp__emberprobe__variables_write  {"values":[{"name":"g_dji_can1_enable","value":0}]}
# 恢复
mcp__emberprobe__variables_write  {"values":[{"name":"g_dji_can1_enable","value":1}]}
```

- 作用范围:**CAN1 全部 DJI 电机**(四轮 M3508 + yaw GM6020);CAN2 的 pitch/摩擦轮/拨盘不受影响。
- 失能时**反馈照常**(电调照发帧、`dt<5ms` 在线判据正常),所以 `odom` / `read_chassis` **照样可以读数和推车测里程**。
- 与"遥控上挡零力"的区别:上挡是底盘/云台任务收到安全态后调 `DJIMotorStop`;总闸是最后一级强制零输出,
  即使上层算出了指令也压成 0,因此**不会被底盘/云台任务顶回去**。两者可叠加。
- 代码位置:`modules/motor/DJImotor/dji_motor.h`(API 与 `DJI_MOTOR_CAN1_ENABLE_BOOT` 编译期初值)、
  `dji_motor.c` 的 `DJIMotorControl()`(`bus_disabled` 分支)。详见 `RM_DEVLOG.md` DEV-20261115-05。

### S0 静态验收(不动机器)

### S1 指令→速度 ⭐(中挡 FOLLOW,落地)

**原理**:`robot_cmd.c:335-349` 右杆归一化成合速度 `CHASSIS_MAX_SPEED`(1500 mm/s),

| 编号 | 操作 | 采样 | 判据 |
|---|---|---|---|
| S1.1 | 右**纵**杆推满前进 5s | 8s,采 `est_vx,est_vy,est_wz` | 稳态 `est_vx` **1350~1500**(打滑会偏低) |
