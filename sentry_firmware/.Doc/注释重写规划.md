# 注释重写执行规划

> 制定:2026-11-09。配套规范:`.Doc/注释规范.md`。
> 目标:把全工程第一方注释统一到一套可传承的风格,**且不引入任何代码行为变化**。

## 1. 出发点:三个月后,读者是作者本人

三个月后回来看代码的人,不会问"这行在干嘛",他会问五个问题:

1. **这个模块为什么存在?** 删了会怎样?
2. **这个值为什么是它?** 谁定的、依据什么?
3. **我改它会打破什么?** 上下游谁依赖它?
4. **上次为什么没走另一条路?** 被否决的方案是什么?
5. **现在哪里是空的?** 哪些是猜的、哪些还没验?

所以注释的价值不在"解释代码",在**保留决策现场**。判断一段注释是否合格,标准是:删掉它,三个月后的作者会不会做错决定。

这也解释了为什么"调大调小会怎样"不能猜——第 2 问的答案如果是编的,比空白更危险。

## 2. 三条不变量(这是减少返工的根本)

| 不变量 | 含义 | 保障手段 |
|---|---|---|
| **代码零改动** | 只改注释字符,任何语句/表达式/宏值都不变 | 剥离注释后比对代码哈希(脚本 `tests/verify_comments_only.py`) |
| **信息零丢失** | 原注释里的数字、单位、DEV 编号、专有名词全部保留 | token 覆盖检查(同脚本 `--tokens`) |
| **每批可独立回退** | 一批一个 commit,出问题整批 revert 不牵连其他 | 按批次提交,禁止跨批混合 |

只要这三条守住,注释重写就是**零行为风险**的操作,可以放心批量推进。

## 3. 分层取舍:先决定"不改什么"

减少改动最有效的手段不是加快速度,是**不做无用功**。

| 文件类别 | 是否重写 | 理由 | 覆盖量 |
|---|---|---|---|
| `application/` 13 个有效文件 | **全量重写** | 业务核心,传承价值最高,现有质量好只需统一 | 100% |
| `config/robot_infantry_2026.h` | **全量重写** | 参数唯一改动点,规范第 5 章的唯一落地对象 | 100% |
| `bsp/` 25 个 | **统一文件头 + 公共接口** | 上游风格最杂(中英混杂、口语化),但内部实现稳定少改 | 文件头 100%,函数头 ~40% |
| `modules/` 自研或高频使用<br>(motor / referee / daemon / message_center / shoot 相关) | **统一文件头 + 公共接口** | 天天调用的接口,注释质量直接影响排障速度 | 文件头 100%,函数头 ~50% |
| `modules/` 上游算法与传感器<br>(kalman / crc / BMI088 / IST8310 / oled 等) | **只补文件头** | 通用算法,不会按本车改,逐行注释收益极低 | 仅文件头 |
| `Drivers/` `Middlewares/` | **不动** | 第三方,AGENTS.md 禁区 | 0 |
| 空壳文件(0 行:balance.h / mecanum.h / steering.h) | **不动** | 无内容可注,是否删除另议 | 0 |

**结论:真正逐行重写的只有 14 个文件(application + config),其余 111 个只做文件头和公共接口。** 这是把工作量从"128 个文件"压到"14 个深改 + 111 个浅改"的关键取舍。

## 4. 执行顺序

### 批 0 · 证据盘点(不改代码)

产出 `.Doc/参数证据表.md`:

- 从 `config` 提取全部 A 类参数(约 40~50 个)
- 逐个 grep `RM_DEVLOG.md` 与 `.Doc/本车调参结论.md`
- 标注:`[实测 日期+DEV号]` / `[理论]` / `[上游]` / `[待实测]`
- 附"知识空白统计":多少参数完全没有数据

**为什么先做:** 不先盘点,写注释时每个参数都要现查一遍,必返工。而且这张表本身就是调参时的工具。

### 批 1 · 样板(2 个文件,先评审)

选两个代表性最强的:

- `application/chassis/chassis.c` —— 有算法、有单位换算、有已知坑
- `config/robot_infantry_2026.h` 的**参数卡片段**(只做前 20 行参数)

产出一份"改前/改后"对照,请用户确认风格。**确认后才批量套用。**

**为什么先做样板:** 风格一旦批量展开再推翻,代价是全批返工。样板是唯一能低成本试错的位置。

### 批 2 · config 参数卡片

按批 0 的证据表,把 A 类参数按规范第 5 章写全。B/C/D 类按简式。

预计增加 120~180 行注释,文件从 ~330 行涨到 ~480 行。可接受。

### 批 3 · application 其余 12 个文件

按依赖倒序:先 `robot_def.h`(协议合同)→ `robot_task.h/.c`(任务骨架)→ 各应用 `.h` → 各应用 `.c`。

`.h` 写契约,`.c` 写实现,严禁重复。

### 批 4 · bsp 25 个

只做:文件头 + 公共接口函数头。上游口语化注释(如"享受开发的乐趣吧!")删除或改为中性表述。

### 批 5 · modules 精选

- 自研/高频:文件头 + 接口
- 上游算法:仅文件头
- 顺手修 `power_control.h` 张冠李戴的文件头

### 批 6 · 收尾

- README 键鼠表补 V/B/G(已知滞后)
- `.Doc/架构与开发指南.md` 增加"注释规范"入口
- AGENTS.md 的 Map 段增加规范文件位置

## 5. 质量闸门(每批必须全绿才提交)

### 闸门 1 · 代码零改动

```bash
python tests/verify_comments_only.py --check
```

剥离所有注释与空白后比对哈希,**任何代码字符变化立即报错**。这是"零行为风险"的硬证据。

### 闸门 2 · 信息零丢失

```bash
python tests/verify_comments_only.py --tokens
```

提取旧注释中的数字、`DEV-YYYYMMDD-NN`、大写术语、单位符号,检查新注释是否为旧集合的超集。防止改写时漏掉关键结论。

### 闸门 3 · 规范自检

```bash
python tests/check_comment_style.py
```

检查:`@file` 与实际文件名一致、无模板占位符、A 类参数有证据标记、无空 `@brief`。

### 闸门 4 · 工程验证

```bash
cmake -G Ninja -B build && ninja -C build     # 0 error,第一方 0 warning
python <skill>/audit_baseline.py --project .   # RedFlags 0
```

### 闸门 5 · 人工抽样

每批随机抽 3 个函数,核对注释与行为是否一致。**这一步不能省**——脚本能查格式,查不了"注释说的是不是真的"。

## 6. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 改写时手滑改了代码 | 引入真实故障 | 闸门 1 强制拦截,不通过不许提交 |
| 删掉有价值的结论 | 知识永久丢失 | 闸门 2 + 改前逐条读,不整段重写 |
| 与并行开发冲突 | 合并地狱 | 一次只改一个文件、改完立即提交;开工前 `git pull --rebase` |
| 注释变长反成负担 | 没人读 | 只在"三个月后会做错决定"的地方写;其余保持一行 |
| 规范执行一阵又散 | 白做 | 规范文档 + 闸门 3 固化为提交前检查;新代码按规范写 |
| 实验数据不足 | 大量 `[待实测]` | 这是**正确结果**,不是失败。标出来即知识地图 |

## 7. 明确的边界

- **不改代码风格**(缩进、大括号、命名)。格式化会污染 diff,且与注释重写混在一起无法 review。要统一格式另开一轮,用 clang-format 单独提交。
- **不新增功能、不修 bug**。看到问题记进 `.Doc/` 或 DEVLOG,不在本工作里顺手改。
- **不删除空壳文件**。删除属结构级变更,需单独批准。
- **注释重写不产生实测数据**。`[待实测]` 需要后续台架实验才能转成 `[实测]`。

## 8. 完成判据

- 所有第一方 `.c/.h` 有规范文件头,`@file` 无错配
- `application/` 与 `config/` 每段注释都能回答第 1 节的五个问题之一
- 参数证据表 100% 覆盖 A 类参数,无未标注项
- 闸门 1~4 全绿,闸门 5 抽样无问题
- 三个月后的作者能只读注释就完成一次参数微调
