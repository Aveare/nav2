# 枪口热量管理设计

> 代码:`apps/infantry/shoot/heat_guard.c/.h`(决策)、`apps/infantry/shoot/shoot.c`(执行)。
> 参数:`config/infantry_2026/config.h` 的"枪口热量守卫"段。
> 本文只写**为什么这么做**,数值理由在各宏的注释里,实测记录进 `本车调参结论.md`。

## 1. 要防的是什么

规则(2026 RMUC 3.3.1)给出的失效链条,三档都不一样狠:

| 条件 | 后果 | 恢复 |
| --- | --- | --- |
| Q1 > Q0 | 锁枪 + 图传断开 | 等 **Q1 = 0** 才解锁,不是回到线下 |
| Q1 ≥ Q2(= Q0+100,17mm) | **整局永久锁** | 无 |
| V1 > V0(弹速) | 15s / 20s / 永久锁(按超速量) | 前两档计时 |

两个推论直接决定设计:

1. **解锁要等热量归零**,所以"刚好越线"的代价是 `Q0/c` 量级(如 240/40 = 6s)的黑屏,
   不是"掉一点血"。这条把安全余量变成极便宜的保险。
2. **永久锁的判定窗口只有 100 点 = 10 发**。6 发/s 下盲打 1.7s 就能撞线。
   因此裁判数据断流必须**降级射速**,而不是"照常打、只报警"。
3. 弹速锁是**另一把独立的锁**,本模块不管;V0 在 0x0201 的 `shooter_speed_limit`,
   每发实测 V1 在 0x0207 的 `bullet_speed`,都需要单独守(见 §6 待办)。

## 2. 为什么不是"热量高了就减速"

从"下达停火"到"裁判侧读到热量"这条链有多段时延:

```
拨盘槽沿 → 弹丸进摩擦轮 → 出膛 → 裁判检测 → 10Hz 结算 → 串口下发
   ~0ms       20~40ms       ~10ms      即时      0~100ms      ~20ms
```

合计 **100~200ms**;同时在这段时间里**还有 1~2 发已经被机械结构吞进去、必然要出膛**。
拿这个带死区的积分对象做反馈,过冲量约等于 `r × T_commit` 发 —— 调参消不掉。

所以本模块的结构是:

```
裁判 ΔQ  ──►  热量估计器 Q̂  ──►  射频规划 r_cmd  ──►  拨盘
（只校模型）      （200Hz 推算）        （无延迟）
```

**反馈打在估计器上,前馈打在执行器上。** 裁判值永远不直接参与"该不该减速"的判断。

## 3. 三个信号,三种职责

不要把"射了一发"当成单一检测问题:

| 信号 | 时延 | 回答什么 | 用途 |
| --- | --- | --- | --- |
| 拨盘槽沿(总角过一发角) | 0~5ms | 推了几发 | **记账**(连发) |
| 双轮转速同时跌落 | 10~20ms | 弹丸进了摩擦轮 | 交叉判卡弹(未实现) |
| 裁判 ΔQ / 10 | 100~200ms | 裁判认了几发 | **校正** Q̂ |

摩擦轮**电流**不作为主判据:电流是控制器输出,量纲与幅值随 Kp/Ki/积分限幅变化,
改一次速度环就要重标;而且它滞后于转速跌落。转速跌落是物理响应(RPM),
不受调参影响,且"双轮同向同时跌落"能把弹丸与卡弹区分开。

## 4. 估计器四条规矩

1. **记账点前移到"放行"瞬间**。放行 = 必然付出这一发,立刻加;等裁判确认会连续漏记 1~2 发。
2. **冷却按 100ms 阶梯扣 `c/10`,不用连续 dt 积分**。裁判是每周期一次性扣,
   连续衰减会在每周期开头系统性低估最多 `c/10` —— 这是唯一会往危险方向偏的建模误差。
3. **不对称校正**:裁判值更高 → 立刻跟随;更低 → 连续 3 帧(300ms)才跟随。
   单帧偏低多半只是裁判帧落后一拍,立刻跟随等于把在途弹的热量抹掉。
4. **Q0 与 c 每帧重取**,不缓存。升级瞬间热量上限会跳变,缓存就会算错阈值。

## 5. 余量与闸门

```
M_burst = 10 × ceil(r × T_commit)   连发:在途弹数量是概率量
M_single = 10                       单发:角度环待发数确定,最多 1 发在途
```

- 连发取 **30**(≈3 发 ≈ 6 发/s 下 500ms),单发取 **15**。
  这也是"到上限只允许单发"的物理理由:切单发等于**买回 15 点可用热量**,不是纯保守。
- 两级闸门:`gate_single = Q0 - M_burst`、`gate_hold = Q0 - M_single`,退出各带 5 点回差。
- 余量按 `Q0 × 0.25` 封顶:低等级 Q0 很小时(如 50 点)固定 30 点会把枪封死。

射速律(`NORMAL` 态):

```
r_sustain = c / 10                                   # 收支平衡点
r_cmd = min( r_demand, r_sustain + (gate_single - Q̂) / (10 × T_spend) )
```

`T_spend = 3s` 决定"余热可以多快花掉"。Q̂ 低时射速受 demand 限制,
逼近闸门时自动收敛到 `r_sustain`,**没有任何阶跃,不会振荡**。

`SINGLE` 态:连发禁止,单发最小间隔 `2 × 10/c`(平衡间隔的两倍,才能净降温)。

## 6. 失效与降级

| 情形 | 判据 | 行为 |
| --- | --- | --- |
| 从未收到有效 0x0201 | `heat_limit` 始终为 0 | `OFF`:全放行(台架/未上线,此时不存在热量) |
| 曾上线但 0x0202 断流 | 300ms 无新帧 | `DEGRADED`:禁止花余热,射速压到 `r_sustain`,单发带间隔 |
| 摩擦轮未到速 | `FrictionReady` 不通过 | 不拨弹(原有互锁,未改) |

判"新帧"用 `PowerHeatTick`(0x0202 帧号),不能比数值 —— 热量在两帧之间可能一字不变。

## 8. 对照:公开实现

- 中科大 RoboWalker 2024 全向步兵 `crt_booster.cpp`:`if (heat <= limit - 30) 全速; else 射速 = c/10`。
  与本文 §5 同构,但没有估计器(直接用 10Hz 原始值),且余量在单发/连发共用 30。
  其"无裁判热量检测"仅到 FSM 文档(`07_no_referee_heat_detect/fsm.md`),代码未落。
- 同济 SuperPower 公开仓库(`sp_middleware` / `sp_control` / `sp_referee`)无热量管理,
  裁判数据在 miniPC 侧解析后下发;其协议注释确认 `cooling_buff` 是**直接值**(点/s)。

## 补充(2026-11-21,DEV-20261121-04):允许发弹量硬闸门

2026 规则引入 0x0208 `projectile_allowance_17mm`(允许发弹量):额度归零后裁判**直接锁发射机构**(断电),
比热量惩罚更硬。热量模型(Q̂ 推算+校正)之上新增一级闸门:

- `projectile_allowance_17mm < 1` → `allowance_blocked=1`,`AllowBurst/AllowSingle` 一律拒绝;
- 做成独立标志而非占用 guard_state:否则与热量闸门互相覆盖,状态每周期抖动、迁移日志刷屏;
- `HEAT_GUARD_ALLOWANCE_ENABLE` 默认 0:台架/未开赛额度恒为 0,启用会永久锁枪;**正式比赛上电前置 1**;
- 客户端日志口径:`允许发弹量:当前|累计透支`(如 `0|-30`),透支在测试台不惩罚,比赛中触发锁定。

同批修复串口接收半死态(ORE 后 re-arm 静默失败 + SOF 错位静默丢帧):守卫的一切逻辑
都以"0x0201/0x0202/0x0208 持续到达"为前提,数据链断则守卫盲,详见 DEV-20261121-04。
