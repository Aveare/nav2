# 兵种分支协作规范

> 制定:2026-11-26(DEV-20261126-39);同日修订(DEV-20261126-230716):DEV 编号改时间戳 + 每人短分支模型。
> 适用于**人 + AI**(含所有新对话的 AI)。
> **读取规则:每个新对话开工前读一次;同一对话内不重复读**——除非本文件被修改、或用户明确要求复述。
> 本文件只管协作纪律;分层/禁改清单见 `AGENTS.md`,多兵种目录结构见 `.Doc/spec/多兵种切换架构.md`。

## 1. 三条铁律

1. **先核对兵种,再动手**:不知道自己站在哪个兵种上,就不写第一行代码。
2. **一个分支只服务一个兵种**:兵种分支上出现其他兵种的改动 = 越界,机器守卫报 FAIL。
3. **共享层改动只经 main 下行**:兵种分支不顺手改共享参数/共享接口,改了就回不去。

## 2. 兵种身份(唯一口径)

| 兵种 | `ROBOT_PROFILE` / `CONFIG_PROFILE` | 应用层 | 参数层 |
|---|---|---|---|
| 步兵 | `infantry` | `apps/infantry/` | `config/infantry_2026/` |
| 哨兵 | `sentry` | `apps/sentry/` | `config/sentry_2026/` |
| 重装 | `heavy` | `apps/heavy/` | `config/heavy_2026/` |

- **当前交付兵种**以各兵种 `.Doc/robots/<robot>/DEVLOG.md` 的状态行为准；根 `RM_DEVLOG.md` 只记公共。
  本文件不固定"当前兵种",只规定核对动作;换交付目标时改那两处,不改本节。
- **兵种 = 代码归属**,不等于"今天调谁的车"。在 `sentry` 分支顺手修步兵 config 也是越界。
- 构建必须显式带兵种:`build.ps1 <robot> -Current` 或 `cmake -B build_<robot> -DROBOT_PROFILE=<robot>`。
  裸 `cmake -B build` 走默认 infantry,**只作历史兼容**,不得当作当前兵种证据。

## 3. 分支模型

参考开源团队实践的形态(仅取方法,不取代码):

| 开源实践 | 本工程落点 |
|---|---|
| Git Flow 的长驻分支(主线 + 开发线) | `main`(共享主干)+ `infantry` / `sentry` / `heavy`(长驻兵种分支) |
| GitHub Flow 的短命分支 + 合并前评审 | `feat/<robot>/<slug>`、`fix/<robot>/<slug>`、`fix/shared-<slug>` |
| Trunk-Based 的小步频繁回流 | 共享修复合入 `main` 后**当天**下行同步到三个兵种分支 |
| Conventional Commits | `<type>(<scope>): <subject>`(见 §7) |
| CODEOWNERS 的路径归属 | §3.3 路径归属表 + `tools/check_robot_scope.py` 机器守卫 |
| Pro Git 的合并点保留 | 短命分支回兵种分支、兵种分支回 `main` 一律 `--no-ff` |

### 3.1 分支职责

| 分支 | 生命周期 | 允许改什么 | 禁止 |
|---|---|---|---|
| `main` | 长驻 | 共享层(`framework/components/ports/tools/tests` 共享件、根构建、`.Doc/`、`.agents/`)+ 三兵种装配骨架 | 只为了某个兵种好调而改共享默认值 |
| `infantry` | 长驻 | `apps/infantry/**`、`config/infantry_2026/**`、步兵专属测试与文档 | 改 sentry/heavy 的目录、改共享层不回流 |
| `sentry` | 长驻 | `apps/sentry/**`、`config/sentry_2026/**`、哨兵专属测试与文档 | 同上(对 sentry 以外) |
| `heavy` | 长驻 | `apps/heavy/**`、`config/heavy_2026/**` | 同上(当前是服务骨架,实车前不得去 SKELETON) |
| `<type>/<robot>/<功能>-<用户>`(如 `feat/sentry/loader-timeout-zhang`) | 短命(≤1 周,功能确认后即删) | 只改本兵种、只做这一个功能 | 从 `main` 切出、跨兵种、推错分支 |
| `fix/shared-<slug>` | 短命 | 共享层 | 夹带兵种参数 |

### 3.2 改动流向

```
fix/shared-* ──merge --no-ff──▶ main ──merge──▶ infantry / sentry / heavy   (下行同步)
<type>/<robot>/<功能>-<用户> ──用户确认功能──▶ <robot> ──验证通过──▶ main   (上行收编)
```

- `main` 只接收两类:①共享层改动;②已在兵种分支编译/测试/实车验证过的兵种改动(整支 `--no-ff` 合入)。
- 兵种分支只接收两类:①个人短命分支(功能经用户确认);②`main` 的下行同步。
- 兵种分支上**不允许**个人直接提交结构级改动;纯文档/DEVLOG 追记可直接提交。
- 兵种分支**不要**直接推 `main`,也不要把两个兵种的分支互相 merge。

### 3.3 路径归属表

| 路径 | 归属 | 兵种分支能改吗 |
|---|---|---|
| `apps/<robot>/**`、`config/<robot>_20xx/**` | 该兵种 | ✅ 只有本兵种 |
| `tests/<robot>_*`、`tests/*_<robot>_*`、`tests/run_<robot>_*`、`tests/<robot>/**` | 该兵种 | ✅ 只有本兵种 |
| `.Doc/robots/<robot>/**` | 该兵种 | ✅ 只有本兵种(文档分库规则见 `.Doc/spec/文档存放与管理规则.md`) |
| `apps/common/**`、`components/**`、`framework/**`、`ports/**` | 共享 | ⚠️ 只走 `fix/shared-*` → `main` |
| `tools/**`、`tests/` 其余共享套件、`.agents/**`、`.Doc/**` | 共享 | ⚠️ 同上(兵种专属文档例外,见下) |
| 根构建文件(`CMakeLists.txt`、`build.ps1`、Makefile、`.vscode/`)、`Src/Inc/`、`Drivers/`、`Middlewares/` | 共享 | ⚠️ 同上,`Src/Inc/` 仍受 USER CODE 区限制 |
| `build*/**`、`firmware/**` | 构建产物 | 不入判定,不提交 |

- `.Doc/` 里的**兵种专属文档**(如 `.Doc/robots/sentry/`)允许在兵种分支修改,
  但提交 subject 必须带兵种 scope;合并回 `main` 时按共享内容处理。
- **文档分库(2026-11-27 起)**:兵种专属文档一律放 `.Doc/robots/<robot>/`(目录即归属);
  共用规则/方法留在 `spec/guide/plan`;过期文档进 `.Doc/history/archive/`。详见 `.Doc/spec/文档存放与管理规则.md`。
- 判不准归属时,按"共享"处理并先问人——**默认更严**。

### 3.4 每人一条短命分支(多人并行时强制)

- **命名**:`<type>/<robot>/<功能>-<用户>`,`<type>` ∈ `feat`/`fix`/`tune`/`test`/`docs`/`chore`;
  `<用户>` 用 ASCII 或拼音(不要中文,URL/CI/命令行都更省事)。
  例:`feat/sentry/loader-timeout-zhang`、`tune/infantry/chassis-power-li`、`docs/shared/spec-rewrite-wang`。
- **基线**:兵种功能从**本兵种分支**切出,不从 `main` 切;共享层/文档从 `main` 切;
  一个分支只做一件事,不夹带无关重构。
- **合并条件(四条全过)**:①该 profile 编译 0 error / 第一方 0 warning;
  ②主机测试 + `python tools/check_robot_scope.py` PASS;③**用户确认功能正常**(台架/实车/可视化验证);
  ④合并前 `git pull --ff-only origin <目标分支>`,合并用 `git merge --no-ff`。
- **未实测的例外**:结构级改动可以先合入兵种分支保持主线可用,但 DEV 条目必须标 `[待实测]`,
  不得声称闭环;实车结论由用户补体系。
- **合并后立即删除**:用户确认 → 短分支合入兵种分支(`--no-ff`)→ 兵种分支验证后合入 `main` →
  **删除本地与远端短分支**(`git branch -d <b>` / `git push origin --delete <b>`)。
  共享/文档类短分支直接合入 `main` 并推送后,同样立即删除。保留 `--no-ff` 合并提交与 DEV 条目即可。
- **长驻分支只有 4 条**:`main` + `infantry`/`sentry`/`heavy`。**其余分支一律视为短命,合并完成即删**,
  避免分支膨胀;不保留"以防万一"的旧分支(已合并提交永远可从主干找回,见 §3.5)。
- **生命周期**:≤1 周。超过一周仍未确认,拆小或回兵种分支重新切,避免长期漂移。
- **不做的事**:不在兵种分支上直接提交结构级改动;不把短分支互相当基线;不 merge 两个兵种分支。

### 3.5 分支清理与找回

收工三件套(每次提交推送后各跑一次):

```powershell
git branch -vv                 # 看本地分支与上游、领先/落后
git branch --merged main       # 列出已并入 main 的分支(含短分支)
git fetch --prune              # 清掉远端已删除分支的本地跟踪引用
```

删除:

```powershell
git branch -d <branch>                  # 已合并的本地分支
git push origin --delete <branch>       # 远端分支
```

找回:

| 情况 | 方法 |
|---|---|
| 已合入 `main` | `git branch <branch> <merge-commit>^2`(合并点的第二父就是短分支 tip) |
| 未合入、本机删了 | `git reflog` 找 tip(默认保留 90 天)→ `git branch <branch> <sha>` |
| 远端删了 | GitHub 仓库 Branches 页 "Recently deleted branches" → Restore |
| 彻底不确定 | 先 `git tag rescue/<branch> <sha>` 再操作,确保对象不被 gc |

**原则:先合并再删;未合并的分支不直接删**(确需放弃时先打 `rescue/*` 标签)。

## 4. 开工核对(每对话一次,顺序固定)

```powershell
git branch --show-current                    # ① 兵种分支,或本人的 <type>/<robot>/<功能>-<用户>
git status -sb                               # ② 工作区是否干净、领先/落后多少
python tools/check_robot_scope.py            # ③ 有无未提交的越界改动(0=PASS)
```

④ 计划改的每个文件,对照 §3.3 说一遍归属;⑤ 构建命令必须显式 `build.ps1 <robot> -Current`。
⑥ 同一兵种有多人并行时,确认自己**不在兵种分支上直接改**,而是从兵种分支切出的个人短分支。

**首次回复必须向用户声明**:`兵种 / 分支 / profile / 验证方式`,例如
`本轮:哨兵 / sentry 分支 / ROBOT_PROFILE=sentry / build.ps1 sentry -Current`。

核对不通过(分支与兵种不符、工作区有越界改动、落后 main 很多)→ **先问人**,
不得在未知状态上继续堆叠;这同时是 `AGENTS.md`「会话开始四步」的第 0 步。

## 5. 要改共享层时的正确路径

1. `git switch main && git switch -c fix/shared-<slug>`;
2. 改共享层 → 编译 + 主机测试 + 闸门(`refactor_gate.py check`);
3. `git switch main && git merge --no-ff fix/shared-<slug>` → 推送 `main`;
4. 三个兵种分支各 `git merge main` 下行同步(至少当前活跃兵种当天做)。

兵种分支上真出现共享改动的两种情况:

- **热修**(修完必须回流):单独一个 `fix(shared): ...` 提交,DEV 条目注明"待回流 main",
  回流后该提交随合并进入 `main`;守卫给出 WARN 而非 FAIL,但不回流会一直 WARN。
- **顺手改**(禁止):为了本车好调去改 `components/` 默认值/共享接口 → 视为越界,必须拆出。

## 6. 兵种结论隔离

- 零位、方向、限位、PID、功率参数**只写本兵种 config**;不得把哨兵标定值抄进步兵 config,反之亦然。
- 抓日志/分析工具默认读当前 profile;跨兵种对照必须在文档里写明来源兵种与日期。
- 写进 `.Doc/robots/infantry/params/调参结论.md`、`参数证据表.md` 的结论要带兵种标记:`[INFANTRY]`/`[SENTRY]`/`[HEAVY]`。
- 兵种专属模块放 `apps/<robot>/<module>/`,不得进 `components/`(见多兵种切换架构 §2.2)。

## 7. 提交规范

```
<type>(<scope>): <subject>  (DEV-YYYYMMDD-HHMMSS)
```

- **编号格式(2026-11-26 起)**：`DEV-YYYYMMDD-HHMMSS`，本地时间精确到秒，例 `DEV-20261126-230716`。
  时间戳只求**全局唯一**，不要求与真实时间严格一致（设备时钟有偏差不致命）；极端撞号时追加 `b`
  （`DEV-20261126-230716b`）并在条目里注明。
- 2026-11-26 之前的 `DEV-YYYYMMDD-NN` 是历史编号：**不改写、不回收**，新条目不再使用序号制。
- `type`：`feat` / `fix` / `tune` / `docs` / `build` / `test` / `refactor` / `chore`。
- `scope`：兵种（`infantry`/`sentry`/`heavy`）或域（`chassis`/`gimbal`/`shoot`/`cmd`/`fwk`/`ports`/`tools`/`docs`/`gate`/`shared`）。
- 一次提交只表达一个意图、只覆盖一个兵种；共享提交用 `shared` scope，不夹带兵种参数。
- 必须对应 DEVLOG 或开发史的 DEV 条目；提交前 `git fetch` 并
  `git log --all --oneline --grep "<编号>"` 自检，DEVLOG 标题与提交标题编号必须一致。
- 已推送的 `main` 与兵种分支：**禁止 amend / rebase / force-push**（唯一例外见 §10 重建记录）。

## 8. AI 提醒义务

AI 不能只在被问时才讲协作,触到下列场景必须主动提醒(短、一次一条、不重复唠叨):

| 场景 | 提醒内容 |
|---|---|
| 新对话首条回复 | 声明兵种 / 分支 / profile / 验证方式 |
| 改动落在其他兵种目录 | 立即停手:"这是 `<别的兵种>` 的路径,确认是否切分支" |
| 多人同兵种并行,或要直接在兵种分支改结构 | 提醒切个人短分支 `<type>/<robot>/<功能>-<用户>` |
| 用户说"功能正常 / 试过了 / 验证通过" | 提醒合并回兵种分支(`--no-ff`)、删短分支、DEV 回填确认结论 |
| 要改 `components/framework/ports` | 提示走 `fix/shared-*` → `main`,并说明回流路径 |
| 提交前 | 对应 profile 编译 + DEV 条目 + 推送(漏一项就不算交付) |
| 烧录前 | 确认 `firmware/<robot>.elf`/`current.txt` 与当前兵种一致 |
| 分支落后 `main` | 建议先 `git merge main` 下行同步再开发 |
| 用户要求跨兵种改 | 提醒需拆成两个分支/两条 DEV 条目;用户明确授权后照做并记录 |

**同一事项在本对话已提醒且用户已确认的,不再重复提醒**;提醒不得打断用户正在做的操作,
放在当条回复末尾一行即可。

## 9. 机器守卫与例外

```powershell
python tools/check_robot_scope.py            # 工作区+暂存(提交前默认)
python tools/check_robot_scope.py --base main # 相对 main 的全部未提交改动
python tools/check_robot_scope.py --range origin/main..HEAD   # 分支级复核
python tools/check_robot_scope.py --strict-shared             # 共享改动也判 FAIL
```

判据:

- 当前分支推断出兵种 `R` → 改动集中出现**其他兵种**路径 = **FAIL**;共享层改动 = WARN(热修)或 FAIL(`--strict-shared`)。
- 一次改动同时覆盖 ≥2 个兵种 = **FAIL**(必须拆分,即使都在 `main` 上)。
- `main`/短命共享分支上改单个兵种目录 = WARN(应落到兵种分支)。
- 已接入 `tools/refactor_gate.py check`,输出一行 `兵种范围`,不改变既有 G1~G6 语义。

例外不设静默豁免:确需跨兵种时,在 DEV 条目写清"改了什么、为什么、如何回流/拆分",
并让守卫 WARN 留在记录里。
