# 注释规范

> 适用:本工程第一方代码(`apps/` `components/` `framework/` `ports/`);历史文档中的 `application/` `modules/` `bsp/` 为升级前路径(B8/B12 已迁)。
> 不适用:`Drivers/` `Middlewares/`(第三方,不改);`Src/` `Inc/` 仅 USER CODE 区。
> 规范来源:Google C++ Style Guide、LLVM Coding Standards、OpenTitan C Style、Clean Code 注释原则。
> 版本:2026-11-09 制定;**2026-11-20 合并《注释重写规划》(原文件已删除)**,补入"为什么写"、
> 批量重写的不变量与质量闸门、分层覆盖范围、批次进度、风险对策与完成判据。

## 0. 为什么写注释:保留决策现场

**注释解释"为什么",代码表达"是什么"。** 写完注释先问一句:这段能不能靠改个名字或抽个函数省掉?能省就省,省不掉才写。

三个月后回来看这段代码的人,不会问"这行在干嘛",他会问五个问题:

1. **这个模块为什么存在?** 删了会怎样?
2. **这个值为什么是它?** 谁定的、依据什么?
3. **我改它会打破什么?** 上下游谁依赖它?
4. **上次为什么没走另一条路?** 被否决的方案是什么?
5. **现在哪里是空的?** 哪些是猜的、哪些还没验?

所以注释的价值不在"解释代码",在**保留决策现场**。判断一段注释是否合格,标准只有一个:
**删掉它,三个月后的作者会不会做错决定。**

这也解释了为什么"调大调小会怎样"不能猜——第 2 问的答案如果是编的,比空白更危险(见 §5.0)。

## 1. 三级注释体系

| 级别 | 位置 | 强制 | 回答的问题 |
|---|---|---|---|
| 文件头 | 每个 `.c`/`.h` 开头 | **必须** | 这个文件在系统里扮演什么角色?分几块? |
| 接口注释 | 公共函数/结构体/宏的**声明处** | **必须** | 怎么调用?参数单位?边界条件?失败会怎样? |
| 实现注释 | 函数体内部 | 按需 | 为什么这么写?这个数从哪来?有什么坑? |

### 硬规则:不重复

- 函数契约写在 `.h`,实现细节写在 `.c`。**同一段话不抄两遍**(Google/LLVM 共同要求)。
- 注释开头**不要重复函数名**。`/** @brief shoot_task 是发射任务 */` 是废话,直接写它的职责。
- 注释掉的代码要么删,要么用 `#if 0 ... #endif` 保留并注明原因和复活条件。

## 2. 文件头

```c
/**
 * @file    chassis.c
 * @brief   底盘应用:速度指令 → 全向轮运动学解算 → 电机参考
 * @layer   APP
 * @author  小猫大王
 * @note    右手系,平面视图中 x 前进、y 向右、z 逆时针为正
 */
```

- `@file` 必须与实际文件名一致(现有 `power_control.h` 写成 `dji_motor.h` 属错误)。
- `@brief` 一句话,不超过 40 字,写**职责**不写实现。
- `@layer` 只能是 `APP` / `COMPONENT` / `FRAMEWORK` / `PORTS` / `CONFIG` / `TESTS`(可带括号细分,如 `PORTS(stm32f4)`;升级前旧值 `MODULE`/`BSP` 已在 B12 归一)。
- `@note` 写整个文件级别的通用前提(坐标系、单位域、线程上下文),可选。
- **@author 署名规则(2026-11-22 修订,F.1,用户指示)**:本队新建/重写文件一律 `@author 小猫大王`(队伍 IP 署名);上游衍生文件**保留原作者行** + 追加一行 `@author modified by 小猫大王`;**上游版权行(Copyright HNU YueLu EC)一律不动**;已有 @author 行在上游衍生文件里原样保留。M3 验收:本队文件 100% 小猫大王、上游原作者行/版权行 100% 保留。
- **不写** `@date` `@version` `@copyright`:靠 git 更准确。AI 协作记录只在 DEVLOG 注明模型名,不进文件头。

## 3. 接口注释

### 3.1 函数

```c
/**
 * @brief  全向轮正运动学解算
 * @param  vx  前进速度,mm/s(云台坐标系)
 * @param  wz  自转角速度,deg/s,逆时针为正
 * @note   输出为电机转子角度域 deg/s,已含减速比与轮周长换算
 * @note   互斥:仅在 chassis_task 中调用
 */
static void chassis_mecanum_calculate(float vx, float vy, float wz);
```

- 标签只用 4 个:`@brief` `@param` `@return` `@note`。不用 `@retval` `@attention` `@warning`,全部并入 `@note` 并加前缀(见 4.3)。
- `@param` **必须带单位**,没有量纲的量写"原始刻度"或"无量纲"。
- 返回值语义不直观时必须写 `@return`(例如返回 0 表示成功、-1 表示超时)。

### 3.2 结构体字段与枚举

```c
typedef struct
{
    float wz;              // 自转角速度,deg/s,逆时针为正
    uint8_t chassis_mode;  // chassis_mode_e 枚举值
} Chassis_Ctrl_Cmd_s;
```

字段注释**右对齐在同一列**,行尾单行即可;超过 40 字改用上方块注释。

### 3.3 宏

```c
#define CHASSIS_ROTATE_SPEED 300.0f // 小陀螺自转速度 deg/s(实测 390 为上限,300 留余量)
```

宏注释必须包含:**单位 + 数值来源**(实测 / 规则 / 标定 / 上游遗留)。

## 4. 实现注释:只写四种内容

### 4.1 为什么这么做(非显然的决策)

```c
/* 切入键鼠的瞬间同步沿计数基线:遥控模式下按过的 Q/R/E/F 不应在切入帧补触发 */
last_q_count = rc->key_count[KEY_PRESS][Key_Q];
```

### 4.2 数值来源(魔法数必须交代)

```c
#define LOADER_JAM_CURRENT 1800.0f // 电流阈值(C610 原始单位,满量程 10000);2026-10-30 台架实测卡弹点
```

**凡是数字,要么有宏名,要么注释说明来源和单位。** 裸数字加"凭感觉"是本工程最容易埋雷的地方(跃鹿上游 `wz = 4000` 就是量纲残缺的经验值,跨工程照抄会直接打满限幅)。

### 4.3 陷阱与前提

```c
/* KBM_YAW_MAX_RATE 改动必须同步 YAW_REF_FF_MAX_RATE,否则大甩时前馈被判跳变静默清零 */
```

风险类注释统一加前缀,便于 grep:

| 前缀 | 含义 |
|---|---|
| `注意:` | 容易踩的坑 |
| `陷阱:` | 曾经踩过、有具体后果 |
| `前提:` | 调用顺序 / 状态依赖 |
| `安全:` | 涉及失控、烧板、伤人 |

### 4.4 历史决策索引

```c
/* 低通只滤帧间抖动,0.6≈3ms 群延迟;回到 0.35(9ms)会明显发钝(DEV-20261106-01) */
```

**格式:`结论句(DEV-YYYYMMDD-NN)`(2026-11-26 起新条目用 `DEV-YYYYMMDD-HHMMSS`)。编号必须有,一句话结论也必须有。** 只写编号让读者被迫去翻 DEVLOG,只写结论又丢了溯源能力,两者都要。

## 5. 参数注释:写清"改了机器会怎样",但只能写有证据的

### 5.0 首要规矩:每条现象都必须有证据等级

**没实测过的参数,写"调大会振荡"就是猜测。猜测写进注释,后人会当结论照着调,比不写更糟。**

所以现象描述必须带证据标记,写在注释第一行方括号内:

| 标记 | 含义 | 允许写什么 | 禁止写什么 |
|---|---|---|---|
| `[实测 2026-11-02]` | 本车台架/实车验证过 | 现象 + 数值结论 + 当时条件 | 超出实验范围的外推 |
| `[理论]` | 控制论/物理推导,本车未验证 | 通用趋势(如 Kp 大→超调) | 具体数值现象("调 10% 抖 3Hz") |
| `[上游]` | 跃鹿或他队默认值 | 原值来源 + "本车未验证" | 当作本车结论 |
| `[换算]` | 纯算术关系(RPM↔发/s) | 可直接写 | — |
| `[待实测]` | 不知道,需上实车 | 含义、单位、调整方向 | **任何现象描述** |

`[待实测]` 是合法且鼓励的写法。它把"这里还有研究空间"显式留给下一个人,比编一段顺耳的话有用得多。

### 5.1 分级要求

| 级别 | 覆盖对象 | 必写内容 | 证据要求 |
|---|---|---|---|
| **A 手感/命中/安全** | 转速、射速、摩擦轮转速、全部 PID 增益、限幅、死区/回差、超时、电流阈值、加速度上限 | 物理含义 + 当前值依据 | 现象部分**必须有证据标记**,无实测则只能写 `[理论]` 通用趋势或 `[待实测]` |
| **B 几何/机械** | 轴距、轮距、轮径、速比、槽数、编码器零位 | 物理含义 + 测量方式 + 拆装后是否需重标 | 测量方式必须真实(卡尺/图纸/数槽),不写"大概" |
| **C 单位换算** | RPM↔deg/s、deg↔rad、mm↔m、原始刻度↔物理量 | 量纲 + 适用数据域 | 标 `[换算]` |
| **D 功能开关** | `*_ENABLE`、调试宏 | 一行说明 + 关掉后果 | 关掉后果写实际的(任务不创建/功能失效),不写"可能有影响" |

### 5.2 三种典型写法

**A 类 · 有实测**
```c
#define CHASSIS_ROTATE_SPEED 300.0f
/* [实测] 小陀螺自转速度,deg/s。
 * 大 → 转到 390 时 yaw 电压已到上限,再大也上不去;300 时轮子无明显打滑;
 * 小 → 未测。目前没有低于 300 的实车数据。
 * 依据:2026-10-30 实车逐档上探至 390 触顶,取 300 留 23% 余量。 */
```

**A 类 · 只有理论**
```c
.speed_PID.Kp = 0.75f,
/* [理论] 偏差→电流的力度。按控制论,偏大→超调/高频抖,偏小→滞后拖慢。
 * 本车未做 Kp 单变量扫描,具体拐点未知;改前先按 0.1 步长试。 */
```

**A 类 · 完全没有数据**
```c
#define SHOOT_RATE_DEFAULT 6.0f
/* [换算/待实测] 6 发/s ≈ 拨盘 1852 RPM,该换算关系确定。
 * 本车射频上限与卡弹边界未实测:调高是否卡弹、弹道是否散,均无数据。 */
```

### 5.3 PID / 结构体成员的紧凑式

结构体里空间有限,用行尾单行,但证据状态不能省——没有 `[实测]` 就在行尾注明:

```c
.speed_PID = {
    .Kp = 0.75f,           // [理论] 偏差→电流力度:大则超调抖,小则滞后拖;未做单变量扫描
    .Ki = 1.0f,            // [理论] 稳态误差累积:大则过冲振荡,小则到不了目标;未实测
    .MaxOut = 10000,       // [换算] 输出限幅(电流给定码 16384 满量程的 61%);限制最大扭矩
    .IntegralLimit = 3000, // [理论] 积分饱和上限;重载顶不住/退饱和慢的拐点未测
}
```

### 5.4 B 类(几何常量)

```c
#define RADIUS_WHEEL 60 // 轮子半径 mm。卡尺实测外径/2;换轮径必须重测,影响全部速度换算
#define NUM_PER_CIRCLE 7 // 拨盘一圈装弹量。数槽数得来;槽数变则 ONE_BULLET_DELTA_ANGLE 自动跟随
```

几何量不写"调大调小",但测量方式必须真实,并写清什么情况下失效(换轮、改机械)。

### 5.5 单位必须写清"域"

同一个物理量在不同层用不同单位,这是本工程最大的坑:

| 层 | 单位域 | 例子 |
|---|---|---|
| cmd 层 | deg/s(物理角速度) | `chassis_cmd.wz` |
| 底盘解算 | mm/s 输入 → 转子 deg/s 输出 | `vt_lf` |
| 电机模块反馈 | 转子 deg/s | `measure.speed_aps` |
| config 标定 | 输出轴 deg 或 遥控器原始刻度 | `LOADER_ANGLE_TOL_DEG`、`dial` |

```c
@param wz 自转角速度,deg/s(物理域,非转子域)
#define LOADER_ANGLE_TOL_DEG 6.0f // 单发到位容差,输出轴 deg(不是电机轴,电机轴要乘 36)
```

### 5.6 写之前必须先反查 DEVLOG

**不得凭印象写参数结论。** 流程固定:

1. `grep -n "<参数名>" $(git ls-files | grep -E 'DEVLOG|开发史|调参结论')` —— 查有没有实测记录
2. 有 → 按 `[实测 日期]` 写,并给出 DEV 编号
3. 只有理论 → 标 `[理论]`,只写通用趋势
4. 来自跃鹿 → 标 `[上游]`,写"本车未验证"
5. 都没有 → 标 `[待实测]`,只写含义和单位

这一步是把 DEVLOG 里的既有实测资产**反向沉淀**到代码里的唯一途径。跳过这一步,注释就退化成个人猜测。

### 5.7 判据

写完一段参数注释,自问两句:

1. **新人能不能答出"车转太慢 / 打太散 / 电机发烫,该调哪个数、往哪边调"?**
2. **答出的每一句现象,都能指出证据来源吗?**

第 1 条答不出 = 只复述了参数名;第 2 条指不出证据 = 这段是编的,拆掉改 `[待实测]`。

## 6. 术语与写法统一

| 统一用 | 不要用 | 说明 |
|---|---|---|
| 云台 | 相机架 / 头 | gimbal |
| 底盘 | 车体 | chassis |
| 拨盘 | 拨弹盘 / 摩擦盘 | loader |
| 摩擦轮 | 摩擦轮电机 | friction wheel |
| 小陀螺 | 自旋模式 / spin | CHASSIS_ROTATE |
| 沿触发 | 边沿触发 / 上升沿 | 按键计数变化 |
| 键鼠 | 鼠键 / KBM 模式 | 图传键鼠链路 |

- 标识符保持英文,注释用中文,专有名词保留英文原文(DBUS、CAN、PID、IMU)。
- 注释里提到代码中的变量/函数名时用反引号包裹:`` `loader_pending` 为 0 表示空闲 ``。
- 单位一律用国际符号:`deg/s` `mm/s` `RPM` `W` `ms`;不用"度每秒""毫秒"。
- 段落分隔线只用一种形式:`/* ---------------- 段落名 ---------------- */`,且只在文件内出现 3 处以上大段落时才用。禁止 `//=====` `//*****` 等纯装饰。

## 7. 禁止清单

1. 复述代码的注释 —— `i++; // i 加一`
2. 过期的注释 —— 改逻辑必须同一次提交内改注释,**错的注释比没有更糟**
3. 注释掉的代码 —— 用 git 找回,或用 `#if 0` + 原因
4. 模板占位符 —— `you@domain.com`、空的 `@brief`、复制来的错误文件名
5. 装饰性分隔线滥用 —— 每 10 行一条
6. 在 `.h` 和 `.c` 里重复同一段函数说明
7. 只写 `@todo` 不写"做什么"和"什么条件算完成"
8. **玩笑、彩蛋、签名式注释** —— 与代码无关,却占据说明位置,读者会误以为它是技术内容
9. **协作污染** —— AI 对话残留(如"下面是 copilot 的回答")、情绪化吐槽(如"什么垃圾协议")、乱码、夸张标点。提交前必须清除,它们比空白更有害

## 8. TODO 格式

```c
/* TODO(2026-11-09): 接入功率控制,前置是 EstimateSpeed 逆解算;完成后删除本行 */
```

必须含三要素:**做什么、前置条件、完成判据**。不写负责人(人换了注释就废了)。

## 9. 本工程高频陷阱(注释必写)

写这几类代码时,注释不是可选项:

| 场景 | 注释必须说明 |
|---|---|
| 单位换算(deg↔rad、RPM↔deg/s、mm↔m) | 输入输出各在什么域,换算系数含义 |
| 来自上游框架的数值 | 是否为上游遗留、能否跨工程复用 |
| 电机反馈方向 | 是否受 `motor_reverse_flag` 影响、符号怎么定的 |
| 跨任务共享变量 | 单写者是谁、读者是谁、要不要临界区 |
| 状态机切换到角度环 | 什么时候切、谁负责切回 |
| 裁判系统字段 | 对应 0x0XXX 哪条协议、字节布局是否被改过 |

## 10. 自检清单(提交前)

- [ ] 新 `.c`/`.h` 有文件头,`@file` 与实际文件名一致
- [ ] 新增公共函数有 `@brief` + 参数单位
- [ ] 新增数字有宏名或来源注释
- [ ] A 类参数的每条现象都带证据标记(`[实测]`/`[理论]`/`[上游]`/`[换算]`/`[待实测]`)
- [ ] 无 `[实测]` 标记的参数,**没有**写具体数值现象(没实测就不许编)
- [ ] 参数单位标明了数据域(物理域 / 转子域 / 输出轴 / 原始刻度)
- [ ] 改动的逻辑,邻近旧注释已同步更新
- [ ] 无 `TODO` 缺三要素、无注释掉的死代码
- [ ] `grep -rn "you@domain.com\|@file  *[a-z_]*\.h$"` 无残留

## 11. 批量重写的执行方法(仅在"统一旧注释"时适用)

日常写代码不需要这一章。它约束的是"一次性改写大量既有注释"这类作业,目标是不引入任何代码行为变化。

### 11.1 三条不变量

| 不变量 | 含义 | 保障手段 |
|---|---|---|
| **代码零改动** | 只改注释字符,语句/表达式/宏值一律不动 | `tests/verify_comments_only.py --check` 剥离注释后比对代码哈希 |
| **信息零丢失** | 原注释里的数字、单位、DEV 编号、专有名词全部保留 | `tests/verify_comments_only.py --tokens` 做超集检查 |
| **每批可独立回退** | 一批一个 commit,出问题整批 revert 不牵连其他 | 按批次提交,禁止跨批混合 |

守住这三条,注释重写就是零行为风险的操作,可以放心批量推进。

### 11.2 五道闸门(每批全绿才提交)

| 闸门 | 命令 | 拦什么 |
|---|---|---|
| 1 代码零改动 | `python tests/verify_comments_only.py --check` | 手滑改到代码 |
| 2 信息零丢失 | `python tests/verify_comments_only.py --tokens` | 改写时漏掉关键结论 |

| 5 人工抽样 | 每批随机抽 3 个函数核对 | **注释说的是不是真的** |

闸门 3 依赖的 `tests/check_comment_style.py` **尚未实现**(截至 2026-11-20)。在它落地之前,
闸门 3 由"人工按 §10 自检清单逐条过"替代。闸门 5 不能省——脚本能查格式,查不了真假。

### 11.3 明确的边界

- **不改代码风格**(缩进、大括号、命名)。格式化会污染 diff,与注释重写混在一起无法 review;要统一格式另开一轮,用 clang-format 单独提交。
- **不新增功能、不修 bug**。看到问题记进 DEVLOG,不在本作业里顺手改。
- **不删除空壳文件**。删除属结构级变更,需单独批准。
- **注释重写不产生实测数据**。`[待实测]` 要等台架实验才能转成 `[实测]`。

### 12.1 分层取舍(先决定"不改什么")

减少改动最有效的手段不是加快速度,是**不做无用功**。

| `Drivers/` `Middlewares/` | **不动** | 第三方,AGENTS.md 禁区 |
