## 0. 一页速查

```powershell
# ── 每天开工 ─────────────────────────────
git pull                        # 先同步

# ── 收工提交 ─────────────────────────────
git status                      # 看改了什么
```

## 1. 新成员首次接入

1. **装工具**：Git（自带 Git Bash）、VS Code、STM32CubeCLT（含 arm-none-eabi-gcc）、CMake + Ninja、一个 gcc（跑主机测试用）。
2. **克隆**（管理员先在 GitHub 仓库 Settings → Collaborators 邀请你）：
   ```powershell
   git clone https://github.com/youyucat/RM-JIT-CR.git
   cd RM-JIT-CR
   ```
3. **配置身份**（邮箱建议用 GitHub 的 noreply 邮箱：`GitHub用户ID+用户名@users.noreply.github.com`，在 GitHub Settings → Emails 页可查）：
   ```powershell
   git config --global user.name "你的GitHub用户名"
   git config --global user.email "ID+用户名@users.noreply.github.com"
   ```
4. **首次验证**（确认环境与仓库状态一致，三件套全过再动代码）：
   ```powershell
   # ① 基线审计(只读)
   "C:/Users/ZhuanZ/.workbuddy/binaries/python/versions/3.13.12/python.exe" "C:/Users/ZhuanZ/.workbuddy/skills/rm-ec-dev/scripts/audit_baseline.py" --project "<工程根>"
   # ② ARM 编译:期望 0 error,第一方 0 warning
   cmake -G Ninja -B build && ninja -C build
   # ③ 主机单元测试
   powershell -File tests\run_chassis_tests.ps1
   ```
5. **读文档**：README → 《.Doc/spec/架构与开发指南.md》→ 《.Doc/spec/必须做&禁止做.md》→《.Doc/spec/本车调参结论.md》。

## 2. 分支与提交约定

### main 是烧录基线

**main 分支必须始终保持：可编译、主机测试通过、实车验证过（或至少无害）。**
上车的固件永远从 main 构建——别人 clone 下来就能用，这是底线。

### 什么改动走哪条路

| 改动类型 | 路径 | 例子 |
|---|---|---|
| 参数级（数值/注释/文档） | 直接在 main 上提交推送 | 调 PID、改零位、更新 DEVLOG |
| 结构级（新文件/新函数/新任务/改接口/改构建） | 开分支 → PR → 至少 1 人 review 后合并 | 加模块、改任务、动 Makefile/CMake |
| 不确定影响面大的改动 | 开分支，实车验证通过后再合 | 投影算法改动、安全机制调整 |

```powershell
# 结构级改动标准流程
git switch -c feat/referee-ui        # 建+切分支
# ...开发、提交若干次...
git push -u origin feat/referee-ui   # 推分支
# GitHub 网页上开 Pull Request → 队友 review → Merge
```

分支命名：`feat/功能名`、`tune/调参项`、`fix/问题描述`。短期分支（几天内）合完就删。

### 提交信息规范

格式：`类型: 中文描述 (关联编号)`，一次逻辑改动一个 commit。

```
config: 小陀螺平移偏置 BIAS -10°→-15° (DEV-20261103-03)
fix: 拨盘单发超时判定改为角度容差 (RM-002)
feat: 新增裁判系统 UI 绘制模块
docs: DEV-20261105-02 记录弹速标定
```

类型：`feat` 新功能 / `fix` 修复 / `config` 参数 / `docs` 文档 / `ci` 构建配置。
**调参类 commit 务必在描述里写清实车验证结果**（如"实车确认轨迹吻合"），这是日后回溯的唯一依据。

## 3. 每日流程

**开工**：
1. `git pull` —— 同步队友的改动
2. 改动过 `apps/infantry/`/`components/` 的，跑一遍基线审计和主机测试，确认基线干净再动工

**收工**：
1. 编译 + 主机测试通过
2. 按《RM_DEVLOG.md》格式补 DEV 条目（AI 修改的也必须写，注明 AI 模型名——AGENTS.md 契约）
3. `git add` + `git commit` + `git push`

## 4. 调参标准流程（高频场景）

```
改 config/infantry_2026/config.h → 编译 → 烧录(实车操作人执行) → 实车验证
   ├─ 达标 → 回填 .Doc/spec/本车调参结论.md + RM_DEVLOG → commit(注明验证结论) → push
   └─ 不达标 → 继续改 → 重复;中间态 commit 前先 git pull 防冲突
```

- 实车标定值（零位、PID 终值）**必须当天回填**进 DEVLOG/调参结论，人记不住昨晚的数。
- 多人同时调不同子系统（底盘/云台/发射）时，都改同一个 `config/infantry_2026/config.h`——**拉取要勤，改动区域错开，冲突及时喊对方**。

## 5. 冲突与撤销

**pull 冲突**：
```powershell
git pull
# 冲突文件会用 <<<<<<< ======= >>>>>>> 标出,和队友当面确认保留哪边
# 编辑完成后:
git add <冲突文件>
git commit                      # 完成合并
git push
```

**撤销操作**（按状态选，别猜）：

| 状态 | 命令 | 说明 |
|---|---|---|
| 改了还没 add | `git restore <文件>` | 丢弃工作区改动，**不可恢复** |
| add 了还没 commit | `git restore --staged <文件>` | 取消暂存，内容还在 |
| commit 了还没 push | `git reset --soft HEAD~1` | 撤 commit，改动保留 |
| 已经 push 到远端 | `git revert <commit-id>` | 生成反向提交，**安全** |

> ⚠️ **严禁** `git push --force` 到 main、严禁 push 后 `reset --hard` 再推——会吃掉别人的提交。实在要回滚远端用 `git revert`。

## 6. 禁令（对齐 AGENTS.md，违反会被要求回滚）

- 不提交：`build/` 固件产物、`.elf/.hex/.map`、大文件（视频/压缩包，>50MB 联系管理员走网盘）
- 不改：`Drivers/`、`Middlewares/`、`Src/Inc/` 的 USER CODE 区外代码、`basic_framework.ioc`（需明确批准）
- 逻辑层 `apps/infantry/` 不直接碰 `hcan*/husart*` 等硬件句柄，一律经模块实例
- 任务启停只用 `robot_task.h` 宏，不注释启停
- 新增 .c 文件必须同步登记 Makefile
- `git push --force`、删除远端分支、改写他人提交：禁止

## 7. CI 自动构建

推送到 main（或开 PR）后，GitHub Actions 自动执行：`make` 全量构建 + CMake/Ninja 构建。
绿勾 = 两套构建系统都编译通过；红叉 = 去 Actions 页看日志，**CI 红着不要往 main 合结构级改动**。

## 8. FAQ

**Q：push 被拒 `remote rejected ... fetch first`？**
A：队友先推了新提交。`git pull` 再 `git push`。

**Q：不小心把 build/ 或大文件 commit 了？**
A：还没 push → `git reset --soft HEAD~1`，把文件从暂存区去掉重提；已 push → 喊管理员处理，别自己 force push。

**Q：commit 写错字/漏文件？**
A：还没 push → 改完 `git add` 后 `git commit --amend`（覆盖最近一次提交）；已 push 就追加一个新 commit，别 amend。

**Q：报错 `CMakeCache.txt directory is different` / `source does not match the source used to generate cache`？**
A：`build/` 缓存里写死的是绝对路径,工程文件夹挪过位置(或改名)就会对不上。**删掉整个 `build/` 重新配置即可**,里面全是可重新生成的产物:
```powershell
cmake -G Ninja -B build && ninja -C build
```
从 git 克隆不会带 `build/`,此问题只在本机移动工程文件夹时出现。

**Q：想看某个参数的调参历史？**
A：`git log -p -- config/infantry_2026/config.h | less`，或 GitHub 网页上打开该文件点 History。
