## F2. 最大的结构性遗漏：整份方案没有"赛季倒排"

方案有 13 个批次、有会話数预估、有关键路径，**唯独没有日历和截止线**。全文未出现任何"赛前 N 个月"、"2027 赛季"、"必须在 X 之前完成"的时间锚。

这与它自己引用的规则手册直接矛盾：手册是 2026-10-15 发布的 **V1.0.0**，说明 2027 赛季准备期已经开始；而 C.3 把 2027 的**全部**功能需求（功率限制复活、launcher_42mm、场地交互、UI 2027 字段、自定义终端、哨兵自主）都推到"M5 后"。

按批次表自行加总（我用的就是方案自己的数字）：B0b 2~3 + B1 3~5 + B2 2~3 + B3 2~3 + B4 4~6 + B5 2~3 + B6 4~6 + B7 2 + B8 5~7 + B9 2~3 + B10 4~6 + B11 3~4 + B12 2~3 ≈ **35~51 个 AI 会话**，另加 3 次实车回归与人工复核。这还没算 F1-2 的补账。

于是出现方案没有面对的取舍：**在一个赛季的准备期里，把全部工程时间投入"零新功能"的重构，而把本年度的全部新功能排到重构结束之后。** 这不是技术问题，是排程赌注，而方案没有把它摆到台面上让用户选。

**建议：§0 或新增 §0.5 必须补一张"赛季倒排表"**，至少包含：
1. 2027 赛季首次需要上车的**硬日期**（校内赛/联盟赛/区域赛，由用户填）；
2. 倒排出的"最后可开工批次"——在该日期前 N 周必须停止重构、留出调参与可靠性验证窗口；
3. 若倒排结果为负（时间不够），方案必须给出**降级版**（见 F3），而不是默认全量执行。

## F3. 缺少"最小可交付切片"与停止规则——这是绞杀式路线真正的风险

方案 L6 用整整一段论证"原地绞杀优于空白重建"，理由是"空白重建无基线，错误只能积累到最终集成才暴露"。这个论证是对的，但它只论证了**路线选择**，没有回答绞杀式路线自己的核心问题：**走到一半停下来，系统是什么状态？**

方案的批次表是线性串行（关键路径 B0b→B1→B2→B4a→B4b/c→B5→B6→B7→B8→M3），而迁移期的中间态是客观存在的：
- B4 之后：`ports/stm32f4` 的 xr_bus **与** 存活中的 `bsp/` 两套总线并存；
- B2~B7 之间（5 个批次！）：`xr_msg` **与** `message_center` 两套消息并存（方案靠适配头过渡）；
- B5/B6 之后：`components/` **与** 残留 `modules/` 两套组件并存；
- B8 之前：`apps/` 与 `application/` 两套装配并存。

**任何一次比赛急务导致的"暂停"，都会停在一个同时存在两套实现的状态上。** 此时"改功能"要改两处或判断改哪一处，冷启动成本翻倍，而方案的 §7 只说"插队须记升级暂停/恢复 DEV 条目"——这只解决了记录，没解决**代码可维护性**。

**建议：为每个批次声明"停止点快照"（stopping point）**，格式：*在第 Bn 批收尾时停下，仓库处于"单一实现 + 可比赛"状态的判据是什么*。据此重排批次，让"无并存态"的批次边界尽量靠前。最明显的一条可操作调整：**把 B7（消息切换）提前到 B2 之后立即做**——xr_msg 的适配头本来就是为了"切换期"存在，让它跨越 5 个批次与 5 次"暂停机会"，收益远小于风险；而消息层是全案最独立、最可主机测试、行为面最窄（6 个话题）的子系统，`[证据]` `chassis.c:165-166`、`robot_cmd.c:114-121`、`gimbal.c:267-268`、`shoot.c:161-162` 确认全仓只有 6 个话题、12 个注册点。

## F4. 前置验证能力缺失，却被排在"迁移之后"

`重构总方案.md` §3.4 自己把"验证能力缺口"标为**本方案最大风险**，并写明续做前提是"先给 heat_guard 与 chassis 纯算术补主机测试"（§9.4）。本升级方案把这条建议**没有采纳为前置**：它把主机测试补充降级为 B5/B6 的验收项（L236 补偿控制①），而 B5/B6 本身正是需要被验证的迁移对象。

更具体的时序空洞：**G8a 纯函数对拍自 B4 起强制，但 B5/B6 迁移的是组件（状态机+时序），G8a 覆盖不到；G8b 整链对拍到 B8 才强制，而 sim 整链"随本批就绪"。** 于是 B5、B6 两个最重的迁移批（预估 2~3 + 4~6 会話，含 IMU/INS/EKF）处在"没有对拍网"的区间，只能靠 G5 符号尺寸 + G2 编译 + 人工读代码。

**建议**：把"补主机测试到可覆盖 B5/B6 迁移面"写成 **B1 的出口判据**（而不是 B5/B6 的验收项）。可落到具体对象：`heat_guard` 两级闸门与 allowance 计算、chassis 正逆解与跟随律、`PIDController`/斜坡、`DecodeDJIMotor` 解码。这些恰好是纯函数或近似纯函数，主机可测，而 `tests/` 已有 3 套框架可复用（`chassis_remote_test.c`、`ax650_*`、`cmd_watchdog_test.c`）。

## F5. 机制冲突：G1'「参数宏逐字节守恒」与 2027 赛季参数切换不能共存

这是全案唯一一处"两个正确目标互相矛盾"，且方案两边都写了、都没察觉到冲突。

- 左侧：§5 G1' 要求 `config/robot_infantry_2026*` 宏集合为上批超集、**禁改禁删参数**；现有执行器是逐字节比较（`refactor_gate.py:234-250`，`dump_macros()` 用 `gcc -E -dM` 导出后 `cur == old`，仅 `--allow-new-macros` 允许"新增"，**没有"允许改值"的通道**）。
- 右侧：附录 C.3.4 与 §3.1 T12 说"赛季切换时新增 `config/robot_infantry_2027/`"。但 2027 参数**必然改值**（步兵对抗赛 200 血/80 热量/120W vs 2026 现行值；单发热量与 Q2 在 42mm 档变化；初始允许发弹量 1V1=200 / 3V3=0）。

再加上执行器的两个硬编码：`CONFIG_H = "config/robot_infantry_2026.h"`（`refactor_gate.py:61`）、`ELF = build/basic_framework.elf`（`:37`）。换伞头、B12 改名 target，G1/G5 立即失效。

**建议**三件事同时写进方案：
1. G1' 增加第三档"**赛季参数切换批**"：允许同名宏改值，但必须输出逐宏 diff 表并声明"属行为变化批、需单独授权"（把赛季切换从"零行为"里显式剥出来，而不是让它悄悄破坏闸门）；
2. `refactor_gate.py` 的 `CONFIG_H`/`ELF` 参数化（`--config`/`--elf`），作为 B1 交付的一部分——否则 B12 会踩到自己埋的雷；
3. 明确 2027 参数目录的**引入时点**：升级期冻结功能，但参数是"资产不是债务"（L115 自己的话），2027 参数必须在赛前某个时点落地。方案要给这个时点。

## F6. G4 的执行器与 G-E 的"退役"自相矛盾（执行层硬冲突）

- §4.1/§4.2（L213-214）：`audit_baseline.py` **退役/封存**，审计口径改为"上批→本批自比"。
- §5 G4（L227）："自基线审计（上批→本批）,Added/Changed 与批次声明一致"。

但执行器现状是：`cmd_check` 的 G4 完全依赖 `audit_baseline.py` 的 5 个计数与 `build/refactor_baseline/audit.json` 比对，路径硬编码在 `refactor_gate.py:60`，计数由它对着**上游 manifest**算出。**退役 audit_baseline.py = G4 立刻失效**，而"上批→本批自比"的替代实现（自比需要"上一批"的文件快照，不是 manifest）**方案没有为它排任何批次、任何工作量**。

**建议**：在 B0（原 B0b）增加交付物"G4 新执行器"：`refactor_gate.py save-baseline` 同时快照**第一方源文件清单+行数+内容哈希**，`check` 改为与上一批快照自比（Added/Changed/Missing 由哈希算出，不再依赖 manifest）。这是"锚定"的字面含义，不做的话 G4 从 B0 起就是空闸。

## F7. 与"全兵种跨平台"的目标相比，这套抽象的最小性没有被论证过

T0 判据里 T05/T06 要求 framework 零 RTOS / 零 HAL 依赖，G-C 又要求 5 个平台后端（STM32F4+FreeRTOS、裸机、x86 sim、Linux、ROS2）。但**当前唯一的真实需求方是 1 台 STM32F407 步兵**；其余 4 个后端的"需求"来自推测（B10 自己写"ROS2/Linux 与比赛主线脱节，不做即不影响 G-F"）。

方案对一车赛队的风险判断是"团队 C 抽象设计经验=中"，但对**抽象层数与收益不匹配**的风险没有条目。第 2 个真实后端出现时，抽象才有机会被"用"出来；在此之前，`xr_os`/`xr_bus` 的接口是**按猜想设计的**，而端口层每多一个后端，就是每批次都要维护的额外约束（framework 禁 `FreeRTOS.h`、禁 HAL 头）。

**建议**：把 G-C 的 5 个后端切成"**当前需要**（STM32F4+FreeRTOS）= 承诺"与"**骨架留位**（其余，不承诺可运行、不排批次）"两档，并在 §1 G-C 明确降级 —— 这不会减少抽象工作量，但会**减少错误抽象的代价**（不用为不存在的能力锁定 API 面）。同时把 B10（Linux/ROS2，4~6 会話）标注为"可整体取消，不影响任何其它批次"，与 B9 同级。

## F8. 一句话总结

技术方案本身的设计质量高于它的**前提管理**：架构分层、契约表、闸门分档这些是认真做的（域B 会逐条评）；但它把"当前状态"写得过于乐观（F1：闸门是红的、B0a 已结束、源列表已漂移）、把"什么时候必须做完"完全留空（F2）、没有定义"中途停下是什么状态"（F3）、把验证能力建设排在被验证对象之后（F4）、并且有两个执行层的自相矛盾（F5、F6）。

**这几条不修，前 3 个批次的每一次"通过"都是对着一个不存在的基线签的字。**
