## 装机后总计划书（三轴合并排程）

产出：`.Doc/装机后总计划书.md`。三份分计划（yaw / pitch / 底盘）各自都写「P1 是第一件事」，
但车只有一辆、首次上电只有一次，依赖是交叉的 → 需要统一时间轴 + 固件批次表。

### 核心设计

- **阶段 S0~S5**：S0 断电机械检查（不烧录，车装好当天可做）→ S1 首次上电安全确认 →
  S2 三轴基线（一次跑车拿完）→ S3 标定（前馈全关）→ S4 补偿落地 → S5 进阶（可选）。
- **六条硬约束 H1~H6**：限位先于满量程、零位先于基线、IMU 轴向先于 pitch 闭环、
  底盘-V3 先于 yaw-B4、pitch-B7 先于 P4 路线、yaw 标定先于 ESO。
- **固件批次 F0~F5**：F0=当前（三 CALIB_LOG 全开）→ F1=零位/限位写回（S2 全程不再换）→
  F2=前馈全关标定 → F3=yaw 库仑+pitch 重力 → F4=pitch 摩擦/滤波 → F5=底盘功率。

### 本轮新增的判断（不在三份分计划里）

1. **单变量纪律要按轴分开**：同轴串行（COULOMB 与 J 不能同版，否则无法归因）；
   **跨轴可并行**（两套独立控制器，不破坏对照性，但验收必须分看）；**底盘独占一轮**
   （底盘参数经关节耦合影响 yaw 的世界系反馈通道）。
2. **S2 第 5 步一次测三件事**：小陀螺恒速时 `ω_joint = ω_chassis`，于是
   外部计时（真值）/ `est_wz`（依赖几何）/ `speed_aps`（依赖编码器）三个独立来源可交叉定位
   ——三者一致则力臂+轮径+yaw 反馈同时验完；不一致按表分流，不要一起调。
3. **pitch 限位实测改为「上电不解锁」**：原计划写"断电手推"，但断电时 IMU 不工作读不出 `Pitch`。
   正确做法是上电但 `stop_flag`（电机不使力），遥控器拔掉作双保险。
4. **功率数据顺带采**：S3 加一段（3 档匀速 + 3 档急加速），趁 F2 在车上采集，
   避免为功率模型单独跑一轮。并给出降级判据：若全程 `buffer_energy` 没掉到 40J 以下，
   功率控制可延到 S5（当前整车小陀螺仅约 22W，加发射/电容后必须重测）。
5. **MVP 线约 12 小时**：S0+S1+S2+（S3-a/c）+S4-7.1。S3-b（J）只服务 ESO，可跳过。

### 代码级确认的事实（写步骤前逐个查过）

- **遥控器右开关是底盘模式的唯一入口**：上挡 `CHASSIS_ZERO_FORCE`（四轮 DJIMotorStop，编码器仍读）、
  中挡 `FOLLOW_GIMBAL_YAW`、下挡 `CHASSIS_ROTATE`（`wz = CHASSIS_ROTATE_SPEED` 写死）。
  **没有 `CHASSIS_NO_FOLLOW` 的遥控/键鼠入口** → 纯平移只能用中挡（要求 offset 在死区内）。
- **中挡硬依赖云台**：`wz = 位置项(offset_angle) + 阻尼 + IMU前馈`，offset 来自 yaw 电机 ecd。
  云台没装/没通电 → offset 是垃圾值 → 底盘一直缓转。判据：中挡静止 10s 应完全不动。
- **450 档跑不到**（本次新算）：`LF_CENTER=(230+250)×DEGREE_2_RAD`，配 `×0.7071×WHEEL_RATIO` 后
  `wz=300` → 转子 25,795 deg/s = **4299 RPM**；`limit=6000×6=36000 deg/s` → 450 档理论 38,693 deg/s
  被削到 **约 419°/s**。100/200/300 → 1433/2866/4299 RPM。
  小陀螺 300 + 平移 1500 叠加 → `vt_lf≈41,190 deg/s` 也削顶。
- 底盘四轮：CAN1，tx_id **LF=4 / RF=1 / LB=2 / RB=3**，`motor_reverse_flag` 统一 NORMAL（只在 LF 前设一次）。
- `[chcal]` 当前 5 列：`vx/vy/wz/gz/be`，0.5s 一行，`CHASSIS_CALIB_LOG=1`。
  自转工况 `gz` 恒 ≈0（云台世界系静止），**不能当底盘转速参照**。
- 改档位要重烧：`chassis.c:293` 是写死宏，三档 = 三次 config 改动重烧。

## 烧录失败诊断（ESP: OpenOCD "error writing to flash" + 退出码 0xC0000005）

**结论：探针 USB 连接不稳定，不是固件/工程配置问题。** 证据链：

1. 首次连接成功：`SWD DPIDR 0x2ba01477`、`device id 0x101f6413`、`flash size 1024 KiB`、
   `flash 'stm32f2x' found at 0x08000000` → 芯片正常、驱动匹配、无 RDP 痕迹。
2. 读 flash 首部为 `ffffffff ×4` → **擦除成功、编程失败**（不是写保护；WRP 会让擦除也失败）。
3. 同一命令的**间歇性失败**：第一次成功 → 连试 3 次全 `cannot read IDR` → 再试一次又成功 →
   最后 `unable to find a matching CMSIS-DAP device`（**USB 枚举层**失败，非 SWD 层）。
4. 降速反而更差（500kHz/100kHz 都连不上，1000kHz 时通时不通）→ 不是 SWD 时序问题。
5. 探针识别为 **XRobot XRDAP（CMSIS-DAP v2）**，VID:PID 0x1d50:0x6199。

→ `error writing to flash` + OpenOCD 崩溃 0xC0000005 = **编程中途 USB 掉线**。
最可能：USB 线/接口接触不良、探针供电不足（车装好后目标板负载大）、或电池/开关没开。

**现场状态：芯片 flash 空（pc=0xfffffffe），车现在不会动，SWD 能连就能救回。**

备用命令行烧录（绕开 EmberProbe）：
`C:/Toolchain/xpack-openocd-0.12.0-7/bin/openocd.exe -f interface/cmsis-dap.cfg -f target/stm32f4x.cfg
 -c "transport select swd" -c "adapter speed 1000" -c "init" -c "halt"
 -c "program C:/RoboMaster/RM-JIT-CR-Infantry/build/basic_framework.hex 0x08000000 verify" -c "reset run" -c "shutdown"`

旁注：program 时报 `flash size = 512 bytes` 与 `no flash bank found for address 0x10000000`
（CCM 工作区相关），但 hex 实测只含 0x0800/0x0801 两段，不是根因。

## 烧录问题最终定性（16:40,三层问题叠加）

**固件已确认写入成功**：一次 1000kHz 烧录后 dump 全部 122336 字节比对，
**只有 8 字节不同**，全在 `0x188-0x18F`（392 字节向量表之后的填充区）：
bin 里是 `00`、片上 `FF`。原因：`objcopy -Obinary` 把段间空洞填 0，`-Oihex` 不记录该空洞。
→ **对固件功能零影响**（向量表止于 0x187）。这也正是 verify 报 `checksum mismatch` 的原因。

**三层问题（按确定性排序）**：
1. **10MHz 提速必失败（已修）**：EmberProbe `openocd-flash.js` 的 `FLASH_SPEED_KHZ[cmsis-dap]=10000`，
   默认 `adapterSpeedKhz=0` 就会请求 10MHz。已在 `.vscode/settings.json` 锁 `1000`。
2. **hex 空洞导致 verify 误报（已绕过）**：烧 bin 而非 hex → 空洞填 0，与片上一致。
   新增 `tools/flash_manual.ps1`（1000kHz + 烧 bin + verify + reset run）。
3. **间歇性通信失败（未解决，需硬件排查）**：同一命令时成时败；失败点包括
   `Failed to write memory at 0x20002xxx`（**写 SRAM** 都失败，与 flash 无关）、
   `CMSIS-DAP command mismatch`、`unable to find a matching CMSIS-DAP device`（USB 枚举丢失）。
   小块读稳定、大块读/写随机失败 → 典型供电不稳或信号完整性。

**排查顺序（硬件）**：①电池供电+开关+3.3V 轨 ②拔插探针 USB（失步后必须重新枚举）
③换 USB 线/后置口 ④烧录时断电机电源 ⑤缩短 SWD 线。

最后确认片上仍有完整固件（`20020000 08013f35 08009dad 08009daf`，与 bin 一致），已 reset run。

## 烧录失败日志串分析（16:52，用户提供 8 次记录）

**重大信息：第一次完全成功** —— 10MHz（不是 1000kHz）、`** Verify Started **` → `✓ 固件校验通过` → `✓ 下载并校验成功`。
→ **证明配置、探针、固件、ELF 格式都没问题；10MHz 也不是必然失败。** 之前归因于"10MHz 必失败"过头了。

后续 7 次失败的模式：
- `cannot read IDR` / `Examination failed`：SWD 层连不上
- `CMSIS-DAP command mismatch. Sent 0x12 received 0x6/0x5`：USB 管道失步
- `Failed to write memory at 0x2000****`：**地址每次随机**（0x2638/0x2590/0x1724/0x0c3c/0x219c）
  → 若是写保护地址会固定，随机 = **通信随机失步**
- 降速到 1000kHz **无效**（第 7、8 次仍失败）

**排除项（都查过代码）**：
- 固件不动 PA13/PA14（SWD 引脚），无 `HAL_PWR_EnterSTOP/STANDBY`，无 DBGMCU 配置
  → 不是固件破坏 SWD
- 不是写保护（地址随机、擦除可成功、能读到 1024KiB flash）
- 不是芯片型号/target 配置（DEV_ID 0x101f6413 / 1024KiB 一直正确）

**结论：SWD/USB 信号质量间歇性失效。** 可能：SWD 排线长/无地回流、探针驱动弱（XRDAP 自制）、
目标板 VDD 不足、车装好后线束与电机线耦合。

**给用户的方案**：①按住 RESET 键点下载（connect-under-reset）②SWD 线 <15cm、GND 双线、远离电机线
③量 3.3V 轨/接电池 ④烧录断电机电源 ⑤换 ST-Link。

**注意**：我这边频繁 `unable to find a matching CMSIS-DAP device`，部分是**与 IDE 抢探针**所致，
不要与 EmberProbe 同时操作。

## 关键反馈：老代码在跑、车轮正常（16:54）

用户实测：芯片里现存**老固件能正常驱动车轮**。三条重要推论：

1. **芯片没变砖** —— 后续多次 `program` 失败**并没有擦掉 flash**（否则车跑不了）。
   说明 `error writing to flash at offset 0x00000000` 发生在**擦除/写入的最开始**就被拒，固件内容得以保留。
2. **供电、电机、底盘链路全部正常**（四轮能转，电流不小）。
3. **问题被收敛到 SWD 这一条链路**，与芯片、电源、固件都无关。
