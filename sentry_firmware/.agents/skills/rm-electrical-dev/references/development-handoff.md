# 工程开发记录与接手规范

## 1. 记录职责

工程主记录回答“当前状态、改了什么、为何修改、如何验证、接下来做什么”。模块 Markdown 描述稳定接口与使用约束；源码注释解释局部实现。三者相互链接，避免重复整段源码或调试过程。

每次实际开发或修改完成、中断前必须更新工程主记录。只读问答、模拟评估或用户明确要求不写文件时，不为记录格式而修改工程。

## 2. 接手与主记录选择

1. 确定工程根目录，使用 `rg --files --hidden` 查找 `RM_DEVLOG.md`、README、开发/交接/问题记录、`.Doc` 和模块说明；排除无关构建目录。
2. 搜索 `rm-electrical-dev`、`handoff`、问题编号及本次功能，先读当前摘要，再读相关历史和源码。
3. 核对有效构建宏、任务入口、硬件配置及最新反馈。原作者不是本 skill 的文档同样需要阅读。
4. 沿用正在维护的主记录及问题编号。没有合适记录时，以 [模板](../assets/RM_DEVLOG.template.md) 创建根目录 `RM_DEVLOG.md`。

本 skill 维护的区域用以下标记识别；标记不改变整份文档的作者归属：

```html
<!-- rm-electrical-dev:handoff schema=2 -->
```

schema=1 或无标记的既有记录均可接手。需要补充字段时保留原历史与作者，记录迁移来源；不强制建立第二份日志或重命名旧文件。

## 3. 记录结构

| 区域 | 必需内容 | 更新方式 |
| --- | --- | --- |
| 当前状态 | 目标、机器人/范围、设计和源码基线、功能/验证状态、问题、下一步 | 随开发更新，引用历史条目 |
| 设计配置 | 相关硬件、板间职责、接口/单位/坐标、依据与待确认项 | 配置改变时更新，链接详细设计文档 |
| 开发进展 | 行为、文件/符号、实际调用链、配置/API/协议影响、验证与遗留 | 按任务追加，保留更正记录 |
| 问题台账 | 稳定 ID、现象、状态、证据、缺项、下一步和关闭条件 | 沿用 ID，更新状态并关联开发条目 |
| 构建与恢复 | 工具版本、命令、宏、依赖、固件身份及换机顺序 | 环境或构建配置变化时更新 |

资料已经存在时使用链接，不复制维护两套配置表。机器专属绝对路径放在环境区域，代码引用使用工程相对路径和符号。

### 阶段切换时的归档（保留溯源、清除误导）

架构/形态大改（如"仅底盘"→整车、单板→双板）会留下与新实现冲突的旧文档与旧脚本。删除会丢失溯源，保留会误导操作（旧接线表、旧解锁流程）。做法：

- 工程根设 `archive/`：`archive/README.md` 为总索引（时间段 | 阶段名 | 归档内容 | 废止原因 | 当前对应物），每段一个子目录并附 README 说明当时架构与等价信息去向。
- 只归档**被废止的第一方资产+说明**，不复制全工程快照（快照属版本管理职责，优先用 git）；归档内容冻结只读，正常开发禁止访问/引用/带入构建。
- 三层溯源各管一段：语义结论（archive 索引）→ 决策与否决（本记录 DEC 台账）→ 字节历史（git）。
- 归档只在阶段切换时进行（**资产归档**）；日常开发条目在功能关闭后按下一节「日志回收」处理，不在阶段切换时归档。

### 功能关闭后的日志回收（DEVLOG 回收）

开发条目只增不减会让主记录无限膨胀，稀释冷启动与故障排查时的信噪比。回收把**已关闭功能**的过程记录搬出正文，结论留在原地。

- **触发（唯一，事件驱动）**：问题台账中某问题转为"已解决"，且关闭条件包含实车或台架证据。**编译通过、主机测试通过不构成触发。** 由用户确认功能正常后执行；AI 只提醒，不自行触发。
- **准入（单条准入，2026-10-27 修订）**：某条开发条目引用的**所有**问题编号均已关闭 → 该条可归档。**不要要求"整个功能簇一起走"**：一条条目常引用多个问题，只要其中一个是长期未关闭的（如整车验收、偶发故障），整簇就永远锁死——2026-10-27 实测 479 行正文里 0 行可动，规则事实上失效。
- **动作（按批）**：①正文原地写 3–5 行结案条目（最终结论 / 最终参数+出处 / 关闭证据 / 会再犯的坑 / 卷宗路径 / **本批覆盖哪几条**）；②本批涉及的原始条目**整段**剪切到 `archive/devlog/YYYY-MM-<feature>/`，保留原始时间与作者、不改写；③`archive/` 索引加一行；④问题台账该条移入"已关闭"，只留 ID/结论/日期/证据指针。
- **两条附加约束**：**更正链同批移动**（被更正的条目必须与其更正条目同批归档，否则正文出现无对照对象的更正）；**分批结案**（一簇可多批回收，每批写自己的结案条目并写明覆盖范围）。
- **批量抽取的坑**：按条剪切时必须**从原始文本一次性重建**（先算出所有保留区间再拼），不要"删一条 → 再用原偏移删下一条"，偏移会失效并误删相邻条目。2026-10-27 实际发生过一次误删。
- **红线**：DEC 台账与**未关闭**问题永不移走；摘要及其他条目引用的内容必须仍可达（归档时把引用改成卷宗路径）；回收只改存储位置、不改结论；回收动作本身不写开发条目（记索引行与提交信息，避免"记录记录"递归）。
- **两类归档规则不同**：阶段切换归档的废止资产属**禁区**；日志卷宗**允许按索引检索**，但只读、**不得作为当前实现依据**，引用时必须注明它已被哪条结案条目取代。
- **阈值兜底**：主记录超过 300 行，或活跃条目超过 12 条且存在已关闭功能簇尚未回收时，提醒用户执行一次回收。

当前摘要链接相关 DEV 条目及问题 ID；摘要只保留最新结论，完整证据在对应历史或详情中维护。

### AI 冷启动摘要

主记录顶部维护固定 schema 的"AI 冷启动摘要"块，AI 会话只读这一段即可接手：基线身份（上游提交/本地改动状态）、有效配置（板型/构建宏/任务入口）、功能状态（已启用/未接）、最近验证分层状态、当前问题与编号、下一个可执行动作。摘要只放结论与链接，证据留在原条目。

### 决策与否决台账

以 `DEC-NN` 编号记录**决策、理由与被否方案**。被用户或验证否决的方案必须入账；未入账的否决会在后续 AI 会话中被原样重新提出。台账条目只追加不删除，翻案时新增条目并引用旧编号。

## 4. 开发条目

使用 `DEV-YYYYMMDD-NN` 或现有编号体系；同一主记录当日序号连续递增。时间使用实际时刻并注明时区。每条至少包含：

- **目标与行为**：需求/触发条件，新增或改变的可观察行为。
- **变更位置**：相对路径及函数、类型、宏；避免仅写“改了底盘”。
- **接口集成**：实际生产者/消费者、调用链、任务上下文；说明 API/协议/配置影响及兼容性。
- **验证证据**：版本、命令或步骤、配置/条件、结果、日志或数据位置；未执行项注明。
- **遗留与下一步**：问题编号、待确认输入、下一个可执行动作。
- **AI 协助标注**：条目由 AI 生成或协助修改时，注明模型与日期；涉及寄存器、时序、手册结论的内容必须保留人工核对记录。

中断时还应标记已保存内容、未完成部分和当前构建状态。发现旧结论错误时追加更正，关联原条目，再更新当前摘要；不改写当时测试事实。

## 5. 问题生命周期

| 状态 | 判定条件 |
| --- | --- |
| 未解决 | 原因未确定或尚未形成满足目标的修复 |
| 待验证 | 已实施候选修复，尚未完成关闭条件所需验证 |
| 已解决 | 关闭条件通过，记录版本、条件及证据 |

阻塞原因单独记录，不替代问题状态。新问题可用 `RM-001` 起始，已有 `E-07` 等编号继续沿用，编号不复用。用户再次复现时重开同一问题并追加新证据。

问题详情应区分已确认结论和候选解释，包含现象/期望、触发、影响、已尝试及无效结果、证据位置、缺项、下一步和关闭条件。实体运动故障不能以编译成功为关闭条件。

## 6. 验证与跨机恢复

分别记录静态检查、完整 ARM 编译链接、烧录、台架、整车状态，并标记“通过 / 未通过 / 未执行 / 不适用”。状态需关联版本和条件；旧记录注明适用版本，不能继承为当前通过。

换机或新对话按“当前摘要 → 问题台账 → 相关开发条目 → 实际源码/配置 → 新构建目录 → 板上固件核验”恢复。skill 版本、记录 schema、上游提交、工程源码身份和板上固件身份分别维护；没有版本号的本地改动需记录改动状态及可复查标识。

记录维护不扩展任务授权。文件写入失败时明确未保存内容并提供恢复方式，不将聊天内容视为已落盘记录。
