# 设计输入与配置确认规范

## 1. 使用原则

先读取工程记录和源码，列出已知项，再询问影响本次开发的缺项。信息收集以任务范围为限：整车新建需要完整设计基线，局部修复只核对相关配置。事实分类按 [上下文管理](project-context.md) 执行。

## 2. 任务与机械基线

| 设计项 | 必须明确的内容 | 适用任务 |
| --- | --- | --- |
| 任务身份 | 兵种、用途、赛事/赛季、功能范围、验收目标 | 新建；其他任务补足相关缺项 |
| 控制分工 | MCU 型号/数量、单板或多板、上位机/飞控职责 | 新建、移植、通信变更 |
| 底盘构型 | 全向轮/麦克纳姆轮/舵轮/差速/平衡等，轮数、布局、安装方向 | 运动学、模式、定位或轮驱开发 |
| 云台拓扑 | yaw/pitch 数量，串联/同轴多驱/独立云台，轴间关系 | 云台、坐标变换或反馈开发 |
| 专用机构 | 发射、供弹、机械臂、夹爪、升降、储能/复位机构 | 对应机构开发 |
| 传感器与计算端 | 摄像头、雷达、定位、IMU、限位等；采集端、处理端、数据接收端 | 相关数据流开发 |

兵种与机械构型分别记录。例如“哨兵”不能确定是否有激光雷达，“双 yaw”不能确定控制分配方式。兵种特有事项见 [兵种设计要求](robot-types.md)。

## 3. 执行器配置

每个受影响执行器使用唯一逻辑名称，并记录以下字段；可采用紧凑索引加单设备详情，避免将全部字段挤入宽表。

| 字段组 | 内容 |
| --- | --- |
| 机械身份 | 逻辑名称、位置/轴、所属机构；同一设备在图纸和代码中的名称对应 |
| 驱动身份 | 电机、驱动器及固件版本、控制模式 |
| 资源归属 | 控制板、CAN/UART/PWM 等接口及端点 |
| 协议绑定 | 设备设置编号、控制帧 ID/组帧槽位、反馈帧 ID；非 CAN 设备记录对应地址/通道 |
| 反馈与量纲 | 编码器/IMU/外部反馈、对应轴、角度/速度/力矩等单位 |
| 机械参数 | 正方向、减速/传动比、零位、软硬限位、负载相关停止动作 |
| 依据与状态 | 分字段说明已确认值、源码现状、测量或待确认项 |

设备编号、CAN 控制帧 ID 和反馈帧 ID 必须分开。核对同总线的反馈 ID、控制组帧及其所有者；不能仅检查设备编号是否重复。具体驱动语义见 [硬件配置规范](hardware-profiles.md)。

## 4. 控制与通信接口

在实现依赖该信息前，明确相关合同：

- 运动控制：坐标正方向、参考轴、量纲、轮序/轴序、传动换算、模式切换和限幅。
- 云台/视觉：反馈所在轴、零位与跨圈、目标数据类型、坐标变换、时间戳、有效期和接管方式。
- 发射/机构：就绪条件、互锁、动作步距、堵转处理、重试上限、退出和恢复条件。
- 通信：生产者/消费者、板间职责、接口参数、包格式/长度/字节序/CRC、版本、频率、超时和恢复。
- 自主功能：定位有效性、任务状态、仲裁优先级、人工接管及降级行为。

规则限值引用适用官方文件；工程配置中的同名常量不能代替来源查证。

## 5. 配置就绪条件

| 工作 | 可开展条件 |
| --- | --- |
| 结构、接口设计及构建检查 | 已明确模块职责；缺失硬件项显式保留，不宣称可上车 |
| 运动学与控制实现 | 相关拓扑、坐标、单位及反馈合同已明确 |
| 实际设备绑定与使能 | 对应型号/模式、资源/ID、方向及必要保护配置已确认 |
| 台架或整车验收 | 设备配置、固件身份、测试条件和验收目标可追溯 |

缺项时提出简短且具体的问题，说明其决定的接口或行为，同时继续不依赖答案的工作。方案建议不能自动升级为确认值；如用未绑定框架验证构建，须记录实现边界和待配置项。
