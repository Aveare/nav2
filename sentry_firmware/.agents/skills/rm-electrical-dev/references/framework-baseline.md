# 跃鹿代码基线使用与维护规范

## 1. 基线身份

随包 `assets/yuelu-basic-framework/` 为 [来源声明](provenance.md) 中固定 GitHub 提交的原始文件副本，包含 APP/Module/BSP、HAL/RTOS/DSP、CubeMX 配置、构建/启动/链接文件、`.Doc`、模块说明与文档资源。文件集合、长度及 SHA-256 记录在 `assets/yuelu-basic-framework.manifest.json`。

来源与完整性核验只证明副本身份。原示例的电机、几何、PID、协议和任务开关需要适配实际机器人；尚未完成完整 ARM 编译链接或硬件验收的层次不得标为通过。

## 2. 新建工程

1. 确认目标目录、兵种/范围和板间职责。将完整副本复制到新的工程目录；目标非空时先检查内容，避免覆盖。
2. 保留 LICENSE、第三方声明、`.Doc` 和必要构建依赖，阅读相关架构指南。
3. 核对板型/MCU、时钟/引脚、启动文件、链接脚本及实际构建配置。
4. 按已确认设计建立 APP 和实例，核对初始化、任务创建及模式开关；保持原层级与 API。
5. 记录设计基线、接口/配置变更与分层验证结果，形成工程主记录。

缺少真实配置时可建立未绑定的结构或接口，不填入假定电机 ID 和使能参数。旧调试脚本与下载配置需核对当前目标和环境后使用。

## 3. 维护已有工程

用户指定了模板目录或原始压缩包时，以该对象核验本次差异，不擅自换用随包副本或另建平行工程。参数适配按[代码规范](coding-contract.md#2-模板内适配优先)直接修改原配置/预留位置，不重排整个工程。

先接手主记录和源码，确认派生版本，再对照本次所需接口进行差异集成。保留已有 APP、资源分配、调参、协议及保护逻辑；模块存在但当前未启用不能作为删除依据。

接口变更同步头文件、实现、调用者、协议两端和构建，记录兼容性。对既有工程的改动保存在工程本身；随包副本继续作为只读来源，便于比较。

## 4. 完整性与换机

核验 manifest 中的文件集合、长度和哈希，尤其保留 `libCMSISDSP.a` 等必要静态库。换机重配工具链路径、构建目录和调试目标；不复用旧 CMakeCache 作为环境验证。

CMake 与 Make 的宏、选项和文件集合分别核对。更新基线需明确新提交并复核受影响接口，不自动混入上游后续变化。

## 5. 重新采集

使用 [vendor_framework.ps1](../scripts/vendor_framework.ps1)：

- `SourceRoot`：官方仓库的干净 Git 工作区根目录，HEAD 等于 skill metadata 的完整提交。
- `SkillRoot`：具有有效 metadata、尚无代码副本和 manifest 的 skill 根目录。
- Windows 检出保留 Git blob 原字节，避免自动换行转换。

脚本核验 origin、HEAD、工作区和原始文件字节；拒绝非 Git 来源、改动工作区、源/目标嵌套、目录根、重解析点及已有副本。选取必要源文件和资源，排除 Git、缓存、产物与工具可执行文件，保留必要 `.a`；复制后对照哈希并生成 manifest。

**重新采集后必须同步**：以新提交重读受影响文件并更新 [代码地图](code-map.md)（定位索引绑定提交内容，含调用链与陷阱清单）；确认 manifest 与快照一致（audit 脚本会自检）；核对 [演进路线](evolution-roadmap.md) 中批次涉及的文件是否仍然存在。

脚本不删除或覆盖目标，不执行源工程脚本或烧录。失败可能留下不完整副本，须检查并使用新的目标重试，不以目录已存在判断采集成功。许可审计和固件验收分别进行。
