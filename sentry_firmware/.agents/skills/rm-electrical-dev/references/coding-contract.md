# 代码、接口与注释规范

## 1. 适用范围

适用于 APP、Module、BSP 的新增与修改。先遵循当前工程及跃鹿 `.Doc` 的命名、组织和注释约定；保持改动范围与任务一致。新增或显著改变的模块同步维护公开接口和模块 Markdown。

## 2. 模板内适配优先

本节是本用户基于跃鹿模板开发的长期原则；新功能需求仍以用户当前授权为准，不借一次参数适配扩大工程范围。

> **架构升级批次豁免（2026-11-22）**：当工程按已批准的架构升级方案（如 `.Doc/plan/自主研发框架升级总方案.md`）执行批次时，本节"默认不新增 C/H""保留原函数名称/不为更干净重命名或格式化"等条款在该批授权范围内**让位于方案批次清单**——新增 framework/ports/apps/components 目录与文件、搬家即改名、单次格式化提交、message_center→msg 替换均按批次批准执行；批次外仍按本节执行。与方案的冲突处置见方案 §11（A15）。

- **分层纪律（长期原则，红旗审计自动检查）。** 逻辑层禁触硬件句柄：apps/infantry/ 内不得直接引用 `hcan*/htim*/husart*/hspi*/hi2c*` 等 HAL 句柄，一律经模块实例接口；单写者：每个消息话题/共享结构体只有一个生产任务；错误上报不挂死：库层禁止新增 `while(1)`，错误经返回码上报统一进入安全态。
- **先找原入口，再改参数。** 对照用户指定的模板、压缩包或已核验基线，找到原Init/Task、初始化配置结构、模式分支及TODO，直接在原位置适配。用户提供的工程不因“更干净”而被换成另一目录或随包版本。
- **保留组织与可读性。** 保留原函数名称、签名、职责、缩进、分段、作者署名和解释性中文注释；沿用具名配置初始化。PID保留在原电机配置结构，公共机器人参数放原配置区，不为单个参数堆叠新宏、配置头或包装函数。
- **使用原实例接口。** 继续组合DJIMotorInstance、motor_init_config_t、PIDInstance、消息中心与原周期电机任务；APP设置参考和模式，由原模块闭环/组帧/发送。禁止新增直接寄存器操作，也不把原对象接口改成APP直接HAL收发、裸CAN缓冲或另一套驱动。
- **模板适配默认不新增C/H。** 不复制出平行应用，不创建替代模块、包装层或自建总调度。保留原消息成员、话题和任务顺序；不为方便查看增加调试结构、时间戳字段或快照接口。
- **不把安全设计自动变成实现扩展。** 在原有机制上核对停止与恢复，不额外引入状态锁、释放锁、看门狗或控制分支。用户明确要求的保护/新功能可在现有预留位置实现；更大接口或模块变化按当前授权判断，不能仅因为已有TODO就视为必须全部实现。
- **必要修正保持局部。** 已确认的单位、边界、类型精度或初始化错误，在原函数/字段做最小修正并说明原因；不要借修复一处边界问题重写整个模块。检查实际函数、状态、消息和调用链差异，不能只以“文件名没变”证明最小改动。
- **调参不等于整定完成。** 区分用户实测值、当前源码值、候选增益和模板占位。未知零位/方向需明确待标定，不将模板示例或历史另一台车的数据当成本车事实。

## 3. 接口一致性

| 项目 | 规范 |
| --- | --- |
| 命名与类型 | 沿用既有 API；新接口与同层模块风格一致，类型明确表达实例及配置 |
| 参数语义 | 声明单位、参考坐标/轴、方向、范围；同名字段跨模块保持同一含义 |
| 生命周期 | 明确实例、配置及反馈指针的有效期和所有权；异步访问不得引用失效局部对象 |
| 调用上下文 | 说明任务/ISR 使用限制、阻塞行为、并发要求和初始化前提 |
| 错误与返回 | 返回值含义与实现一致；异常处理不能静默伪装成功 |
| 协议变更 | 同步序列化、解析、长度/字节序、两端版本及兼容处理 |

接口调整核对声明 → 实现 → 全部调用者 → 配置/消息类型 → 任务与构建。文档与旧 API 命名不一致时，以核验过的实现为依据，不为形式统一批量重命名。

## 4. 注释职责

- **公开头文件**：描述用途、参数/返回、单位/参考轴及非显然约束。相邻接口共享明确合同后，可缩短重复说明。
- **实现文件**：说明公式与坐标换算、算法依据、状态进入/退出条件、保护逻辑和设计原因。
- **配置定义**：解释物理含义、来源与约束。未确认值标明待确认并关联问题，不填入具有实际使能含义的猜测值。
- **TODO**：描述具体未完成项并关联稳定问题编号；不要保存聊天过程。

常规赋值、明显的函数调用及标准循环无需逐行注释。修改行为时同步相关注释；文件日期和开发历史记入工程 Markdown。

### 公开接口示例

以下仅说明模板已有接口的注释形态，不要求改原声明或新增包装API：

```c
/**
 * @brief 按配置注册一个DJI电机，返回模板电机实例。
 * @param config 已确认的电机类型、CAN绑定、闭环及PID配置。
 * @return 注册后的电机实例，由原电机任务统一计算和发送。
 * @note 初始化阶段调用；PID输入单位必须与所选反馈一致。
 */
DJIMotorInstance *dji_motor_init(motor_init_config_t *config);
```

- 参数注释写清物理含义、控制轴/坐标系、单位、正方向、有效范围及来源；区分转子与输出轴、degree与rad、RPM与degree/s、原始协议给定与物理V/A。
- 优先按原反馈单位换算原PID参数，避免为了单位换算新建反馈层；换算公式就近简短说明，不直接照抄另一单位下的增益。
- 原有函数头和分段注释保留，修改行为时只同步受影响说明；不要批量替换成新风格、给显然赋值逐行加注释，或用大段“保护/调试框架”说明掩盖控制逻辑。
- 代码中不保存聊天、道歉、尝试流水账或“以前助手改错”的叙述；变更历史和候选参数验证状态写入现有工程记录。

实现侧应注释“为什么执行限位/回退”或“当前角度属于哪个轴”，不重复“给变量赋值”。复杂变换注明公式依据、输入/输出量纲及验证用例；数值来源应可追溯。

## 5. 文件与模块文档

保持原缩进、UTF-8 编码和局部风格。CubeMX 生成文件中用户修改保留在 `USER CODE` 区域；仅在用户已授权的新模块开发确需新增源文件时，同步实际使用的构建系统。避免整体格式化无关生成代码。

新增/显著改变的 Module/BSP 文档应包含：用途与职责、文件结构、公开接口/类型、关键实现约束、最小集成用例、验证与限制。工程主记录摘要此次集成并链接该文档；详细硬件配置不重复放入多个模块说明。

## 5. 注释与文档

逐行注释解释"为什么"；函数头说明用途/参数/返回值/关键注意事项，随实现更新。公开接口在 `.h` 给出完整 Doxygen，实现文件仅说明内部逻辑；同一函数的声明和实现注释不重复。解释术语与逻辑链条，而非字面复述代码。原有注释的框架与风格优先继承。

**新文件头格式（统一模板）**：

```c
/**
 * @file    <文件名>
 * @brief   一句话职责
 * @author  JIT CR
 * @date    <创建日期>
 * @note    修改记录见 RM_DEVLOG.md 对应 DEV 条目
 */
```

- 新建文件一律带此头；**修改上游/既有文件时不得覆盖原 @author**，按跃鹿惯例在其头内追加一行 `@author modified by JIT CR (<日期> <事由>)`；与基线逐字节一致的未修改文件不加头（保持审计差异集干净）。

## 6. 修改检查

先对照基线查看是否多了函数、全局状态、消息字段、任务、文件或硬件访问，逐项确认属于本次目标；参数任务通常无需这些变化。再检查实现与接口合同、注释、调用者、协议和构建是否一致。检查单位转换及边界条件是否可追溯，是否引入未初始化调用、失效指针或第二个资源所有者。验证要求由实际变更决定，不为简单局部修改建立重复实现的测试。

**测试资产同步（硬性条款）。** `tests/` 下的主机测试是第一方资产，与源码同等受基线审计管辖：源码行为变更必须同步更新对应测试用例后一起交付；测试引用的符号/行为与当前源码不一致即为交付阻塞（不得以"测试稍后再修"交付，参见工程 RM_DEVLOG DEC-004 退役教训）；测试中允许使用 while(1) 循环（审计红旗已排除 tests/）。
